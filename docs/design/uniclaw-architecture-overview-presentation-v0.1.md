## 0. 一句话定位

> **UniClaw 是一个"眼见为实"的智能执行系统：让 AI 操作真实设备时，可以被信任。**
> 别人做更聪明的 Agent，我们做可以被信任的执行——**先取证、再判断、后动手、动手必验证**；
> 完成要有证明，不确定就诚实说不确定。

三个可以写在 PPT 封面上的短语：

- **证据驱动**（Evidence-driven）：看到 ≠ 相信；一切世界判断建立在登记合格、带来源的证据上。
- **三权分立**（Separation of powers）：想（Control）、裁（Assurance）、干（Effect）由三个互不越界的组件各自持有唯一权威。
- **失败即关门**（Fail-closed）：任何不确定一律安全拒绝；绝不"先试试再说"。

- **能力集**（Capability Set）：可扩展、可替换、可管理——能力皆插件，扩展不修改核心。

> 讲法提示：开场 30 秒只讲这一段。听众记住"眼见为实 + 可以被信任"即可，其余都是论据。

## 1. 信任鸿沟：为什么需要这样一个系统

设想一个真实场景：你让 AI 自动化操作一台车机，它跑了半小时，点击了两百次，然后汇报"全部成功"。
此刻你面对三个不敢签字的问题：

1. **点了没点？** ——它说点了，但你没有独立证据。
2. **点错了谁拦？** ——如果它点了"恢复出厂设置"，谁在中间拦截？
3. **说完成了，真的吗？**——"执行完毕"是模型的话术，还是可验证的事实？

这就是当前行业的**信任鸿沟**：模型能力在涨，但"敢不敢把真实设备交给它"取决于架构，不取决于模型智商。

> 讲法提示：客户在此点头（他们被咬过），开发者在此好奇（你怎么解）。不要急着讲架构，先让问题停留十秒。

## 2. 行业现状：四种典型失败模式

把当前 LLM GUI Agent（含各类 "computer-use" 方案）的常见事故归纳为四类：

| # | 失败模式 | 具体表现 | 根因 |
|---|---|---|---|
| F1 | **幻觉当真相** | 把想象中的控件当成屏幕上存在的，对着不存在的按钮"点击成功" | 模型输出直接进入执行层，中间没有证据层 |
| F2 | **回执当成功** | 指令发出=任务完成；截屏黑了也说"已点亮" | 没有动作后验证义务，尝试（attempt）与效果（effect）混为一谈 |
| F3 | **无人拦险** | 模型自信地执行越权/危险操作，没有独立的安全裁决 | "规划"和"执行"同体，没有分权 |
| F4 | **不可复现** | 同一任务两次运行结果不同，无法回归测试 | 缺乏确定性仿真与证据化回放 |

**关键论点**：这四种死法没有一个是"模型再聪明一点"能解决的——它们是**架构缺位**，提示词约束不住结构问题。这就是 UniClaw 选择做"执行系统"而非"更强模型"的原因。

> 讲法提示：F1–F4 会在后文逐一对应到架构构件（§4–§6），形成"问题→答案"闭环。

## 3. 设计哲学：三条公理

整个系统从三条公理推导出来，全部是**结构保证**而非提示词保证：

**公理一 · 眼见为实（三层分离）**

```
Reality（现实）          屏幕的真实状态——永远只能逼近，不能直接读取
   ≠ Evidence（证据）    登记合格、带来源的观察记录
   ≠ Belief（世界观）    系统基于证据形成的当前判断（版本化、可修正）
```

推论：模型输出只是"观察提案"；准入（admission）只查记录合格不合格，不判真假；世界观的每次更新都带完整证据清单；两个证据冲突时**并存记录，不静默覆盖**。

**公理二 · 三权分立**

```
想（Control Loop）    签发"我想做什么"的意图——唯一意图权威
裁（Assurance）       裁决"可不可以做、够不够新、安不安全"——唯一裁决权威
干（Effect Boundary） 执行已授权动作的唯一出口——唯一执行权威
```

推论：三者任何一个都不能单独完成"想+裁+干"全链路；外部能力（模型、驱动）无论多强，拿不到任何一项权威。

**公理三 · 失败即关门 + 动手必验证**

- 任何不确定（目标歧义、世界观过期、结果未知、证据不足）→ 一律安全拒绝或诚实标注"未知"，绝不带着疑问继续。
- 每次对现实世界动手之后，**必须**重新观察并验证"世界真的如预期改变了"，验证清偿之前禁止下一个现实动作。

> 讲法提示：三条公理各配一个失败模式：公理一治 F1，公理二治 F3，公理三治 F2；F4 由 §7.2 治。

## 4. 架构总览

### 4.1 系统上下文：五大件

```
 👤 用户 ──"把设置菜单全测一遍"──▶ 🧠 大脑 UniAgent
                                   （拥有：目标 · 契约 · 最终评价）
                                      │ 交付契约          ▲ 一次性交卷信封
                                      ▼                  │
                              ⚙️ 执行核 Uni Kernel ◀─────┘
                              （六域分工 · 合法激活后自驱推进）
                                      │ 已授权指令      ▲ 观察提案
                                      ▼                │
                              🔌 能力面 Capability Plane
                              （可扩展·可替换·可管理的类型化能力集）
                                      ▼
                              📱 设备 / 屏幕（Android 车机 · 浏览器）
```

| 组件 | 角色 | 拥有 | 刻意不拥有 |
|---|---|---|---|
| **UniAgent（大脑）** | 认知中枢 | 目标解释、全局策略、执行契约、满意度评价 | 世界观、动作授权、运行状态——不碰 |
| **Uni Kernel（执行核）** | 聚合执行边界 | 组合纪律、唯一结果出口 | 六域各自的真相——一个都不代管 |
| **Capability Plane（能力面）** | **可扩展·可替换·可管理**的类型化能力集（三性质与三类能力见下方） | 产出原始工件、类型化提案、候选绑定、机械回执——**全部只是提案** | 任何"真相"与授权；能力强弱不改变权限 |
| **Memory System（记忆）** | 历史经验回流（设计边界见 §7.4） | 持久记录、溯源、保留策略、召回产出 | 永不单独当作"现实"的依据 |
| **双宿主** | DSH=产品线 / Codex=仿真线 | 装配**同一个**运行时工件 | 仿真路径不进产品闭包 |

**UniAgent 也是可插拔的：五层装配链**（与能力面的四层装配互为对偶，ADR-0041/0022）：

```
① Profile（产品身份）   身份 · 能力声明 · 规划姿态 · Skill 约束 · 模型角色必需性
                         ——不含 provider/model 名与端点（产品身份与宿主解耦）
② Skills（领域 SOP）     有边界的标准作业程序（如 android-automotive-ui-testing）；
                         name/revision/sha256 锚定，allowlist 管理
③ Prompt manifest（纪律）静态分节：身份 / 输出纪律 / 载荷形状；hash 锚定
④ Host 绑定（宿主映射）  provider/model/端点——只存在于宿主侧；换模型换宿主
                         零改产品身份
⑤ Realization（实现体）  Codex=仿真线 / DSH=产品线，整体可替换
```

**可优化的机制与它的护栏**：①②③ 三层都可独立版本化演进——升级 Skill guidance、
调 Prompt、换更强模型，都是配置版本变更而非架构变更。护栏是 **Conformance
Surface 的最小场景集（C1–C11）**：同一用户意图在改动前后必须产出语义等价的
Goal/Contract/Evaluation 记录才算通过；双 realization 还可做差分对比（同一场景
两个宿主各跑一遍，验证宿主无关性）。买到：**优化不失控**——模型、提示词、SOP
怎么换，产品语义不漂移。

**Capability Plane 的自我介绍**（按基线 §8 口径，不化简）——一个**可运营的能力集**：

> "我是承载**可替换类型化能力**的架构面。我接收有界输入，产出四种东西——原始工件、
> 类型化提案、候选绑定、机械回执——并且声明 provenance、置信、不确定度、延迟与
> 失败语义。但我**不创建证据编号、不形成世界观、不裁决、不形成正式绑定、不宣布
> 效果或终局**；我的能力强弱也不改变我的权限。"

**能力集的三个运营性质**（对外介绍的抓手）：

| 性质 | 含义 | 机制（已落地） |
|---|---|---|
| **可扩展** | 新能力 = 实现既有协议缝 + 注册入集，**不改核心** | 每类能力声明协议接口（语义感知 / 元素感知 / 投递驱动…）；有正式的能力接入开发协议与验收清单；扩展发生在缝上，不在核心上打补丁 |
| **可替换** | 同一定义可换实现：仿真 ⇄ 真件、模型 A ⇄ 模型 B、快 ⇄ 慢 | 四层装配中「实现」与「定义」分离；替换只改变质量、成本、延迟——权威链零改动 |
| **可管理** | 从注册到退役全程受治 | 按信任域分立的注册表；task-scoped 绑定（任务结束即关闭，不回写全局）；健康聚合与降级；内容寻址的身份与版本 |
三类能力（都在这一个平面上，"眼/手"只是比喻，不是组件名）：

| 类别 | 例子（本系统已落地） | 产出 |
|---|---|---|
| **观察侧**（比喻"眼"） | 截屏采集；元素/语义感知——快通道 YOLO+OCR、慢通道语义大模型（异步）、UI 层级 XML；定位候选生成 | 观察提案 / 候选绑定 |
| **行动侧**（比喻"手"） | 设备投递驱动——adb、浏览器原生操作 | 机械回执（完成/失败/结果未知 三态） |
| **支撑侧** | 语义理解与推理类能力、模型管理、语言检查、（未来）记忆召回 | 各自的类型化产出 |

四层装配（同一个能力的四个生命周期切片）：**定义**（承诺什么语义与失败语义）→
**实现**（谁来兑现：模型/外部服务/内部算法）→ **绑定**（装配进哪个宿主/任务，
task-scoped）→ **实例**（本次运行的运行体，不回写全局注册表）。

两条铁律：① 一切产出只是**提案**，裁决权全部在执行核六域；② **能力强弱不改变
权限**——换更强的模型不会换来任何越权。

两个容易被忽略但很重要的设计：

- **自驱而非遥控**：契约一旦被接受并合法激活，执行核自己推进到终局；大脑只在"语义决策点"被咨询（例如"这两个方案选哪个"），不逐步遥控。这保证了执行纪律不随模型对话漂移。
- **1:1:1 基数**：一次会话 : 一个目标 : 一次运行。多任务/多运行是显式登记的未来解锁项，不是当前承诺（诚实边界见 §7.3）。

### 4.2 两条大循环（系统主图）

系统的全部工作 = 蓝色"看清楚"循环 + 橙色"做并验"循环，周而复始直到交卷：

```
     📱 设备
      │ ①新鲜截屏                    ⑤已授权指令（闸门放行后）
      ▼                                     │
 🔌 能力面 Capability Plane ──②观察提案──▶ ⚙️ 执行核 ──┤
   观察侧(眼):YOLO+OCR(快)                 ┌───────────┴───────────┐
   语义模型(慢·异步)           │ 证据账本 ──▶ 世界模型 │
   UI层级:XML                     │（蓝色：认识世界）      │
      ▲                        │ 控制环 ──▶ 效果边界 ──▶ 安检 ──▶ 闸门
      │                        │（橙色：改变世界）      │
      └═══③⑥绿色验证回流═══════┴───────────────────────┘
          （⑤落到屏幕后，必须①重新观察→并入世界观→安检确认"真的变了"）
```

- **蓝线（证据流）**：设备 → 能力面·观察侧 → 证据账本（准入） → 世界模型（新版本） → 决策输入。
- **橙线（效果流）**：控制环（意图） → 效果边界（锁定目标） → 安检（裁决） → 闸门（放行） → 能力面·行动侧驱动 → 设备。
- **绿线（验证回流）**：动手后强制重新观察，回执（receipt）≠ 效果（effect）。
- **紫线（咨询流，图中省略）**：执行核只在语义决策点问大脑，一问一答带关联号，答案也只是"建议"，仍须走完整橙线。

### 4.3 执行核内部：六域分工

每个域持有一项**唯一权威**；表格右列"它不做的事"与左列同等重要——这是杜绝"上帝对象"的关键：

| 责任域 | 唯一权威（只有它能做） | 刻意不做（别人也不许做） | 类比 |
|---|---|---|---|
| **证据账本** Evidence Ledger | 证据准入：记录完整性、来源可溯性 | 不判真假、不判相关、不判够不够用 | 证据管理员：只管登记合格 |
| **世界模型** World Model | 世界观版本：屏幕上有什么、状态如何 | 不拥有目标；不接受"期望"改写观察 | 测绘员：画地图不指挥行军 |
| **运行模型** Run Model | 运行状态：契约视图、进度、义务、终局记录 | 不判断"证明成立与否"（只记录安检结论） | 考务处：发卷计时归档 |
| **控制环** Control Loop | 意图签发：下一步观察/行动/恢复 | 不能直接动手、不能自证安全 | 提出动议的议员 |
| **安检** Assurance | 裁决：可否做/够不够新/安不安全/效果真没真/完成成立否 | 不签发意图、不执行动作 | 法官 + 质检章 |
| **效果边界** Effect Boundary | 目标绑定 + 一切现实动作的唯一出口 | 不做策略、不重试、不扩权 | 法警：只执行判决书 |

（各组件「为什么这样设计」的对比与优势，见 §4.6。）

### 4.4 三条冻结流水线

执行核内三条流水线的**次序固定、不可合并**——这是全部正确性的来源：

```
A 观察（认识世界）  admission 准入 → relevance 相关吗 → reconciliation 并入世界观
B 行动（改变世界）  intent 想做 → bind 锁定目标 → judge 裁决 → gate 放行
                    → dispatch 执行 → receipt 回执 → 回流留痕
C 终局（交卷）      proof 证明成立 → terminal 终局记录（冻结）→ outcome 一次性信封
```

细节两则（开发者听众加餐）：

- B 线的裁决绑定**三件套**（意图+绑定+世界观版本）——三者任一变化必须重裁；裁决被拒不销毁绑定对象（"有效"≠"授权"分离）。
- B 线的闸门放行前，先把执行要素登记进 **append-only 执行台账**——进程崩溃后能对账"哪些发了没收条"，未决动作可发现、可补偿，但绝不盲目重发。

### 4.5 协议面（开发者专场页）

组件间共 26 条协议边（P1–P26），每条锁定：生产者/消费者/最小载荷/失败语义/禁止用途。挑六条关键边：

| 边 | 语义 | 一句话 |
|---|---|---|
| P2 | 观察提案 → 证据账本 | 所有观察的唯一入口；投递回执也走这里（但永不充当世界证据） |
| P8 | 意图 → 安检/效果边界 | "想做什么"；不是命令更不是授权 |
| P10 | 绑定 → 安检 | 唯一合法目标绑定，钉死在特定世界观版本上 |
| P13 | 裁决 → 闸门 | 三件套一次性判定；闸门只执法不重判 |
| P15 | 执行结果 → 效果边界 | 三态：完成/失败/**结果未知**——未知唯一后继是重新观察，永不盲发 |
| P18 | 交卷信封 → 大脑 | 一次性发出、不可改、发出后闸门永久关闭 |

> 讲法提示：协议"锁语义不锁实现"——组件可以整体替换（C#/Python/另一个模型服务），协议语义不漂移。


### 4.6 核心组件的设计优势（为什么这样设计）

> 讲法提示：本节是架构走查的加分段——每一项按「天真做法 → 我们的设计 → 买到的优势」三段讲，开发者听众最容易在此建立尊重。

| 组件 | 天真做法（常见实现） | 我们的设计 | 买到的优势 |
|---|---|---|---|
| 🧠 大脑 UniAgent | 一个模型全包：想、干、自我评价 | 认知与执行分离；只在语义决策点被咨询；评价只读事实、不回写 | 换模型不动执行纪律；「完成」= 执行侧可证事实＋认知侧解释，两权不串 |
| ⚙️ 执行核 Uni Kernel | 多个入口都能触发设备动作 | 一切外部效果过闸门；唯一交卷口；终局后关门 | 审计面收敛——查一处即查全部；「僵尸运行」结构性不存在 |
| 📚 证据账本 | 感知输出直接当事实用 | 准入只查记录合格（来源/时间/范围/血缘），不判真假；append-only | 反幻觉的第一道结构闸：模型说的永远只是「申报」；证据不可篡改、全程可溯 |
| 🗺 世界模型 | 维护一份「当前真相」，新数据覆盖旧数据 | 版本化判断；冲突双方证据并存；一切判断锚定版本 | 「过期」可精确判定（绑定/裁决都钉版本）；不丢反例；两次运行可比 |
| 📋 运行模型 | 进度由执行者自己汇报 | 义务清单化；满足判定归安检、运行模型只记录；终局一次冻结 | 「完成」是义务×证据的核对表，不是话术；terminal 后不可复活 |
| 🎮 控制环 | 把 LLM 生成的计划当状态推进 | 战术假设随时可被新证据作废；意图唯一签发；恢复必须重入闭环 | 世界变了计划立刻让位；禁盲重试，恢复也是受控行为 |
| ⚖️ 安检 | 执行前自查一遍（自己给自己签字） | 独立裁决；「意图＋绑定＋世界观版本」三件套；新鲜度按本次消费判定 | 授权语义精确可审计；「够不够新」有显式答案；拒绝≠失效 |
| 🚪 效果边界 | 拿到坐标就点 | 可执行目标只来自当前授权绑定的降级；闸门只执法；执行前 append-only 登记 | 点的永远是「裁决过的那个」；崩溃后可对账未决动作，绝不盲补发 |

两个「看起来不起眼」的同构优势：

- **记忆（Memory）**：占位但先钉死边界——recall 永不单独当作现实依据。买到：**记忆不污染当下**（历史经验只能当假设，不能当证据；三个优化循环见 §7.4）。
- **追踪（Trace）**：非权威投影——观察面永远不能成为命令面。买到：**可观测不夺权**（出事能查，但查的权限动不了系统）。

## 5. 一次点击的完整旅程

### 5.1 十步主路径

1. **截图**：从设备取新鲜画面（内容寻址的原始像素）。
2. **感知**：快通道 YOLO+OCR 毫秒级出元素；慢通道语义大模型异步补理解；UI 层级 XML 第三路佐证——三路都只是"观察提案"。
3. **准入**：证据账本登记：来源/时间/范围/ lineage 齐全才收；不齐明确拒绝（零副作用）。
4. **并入世界观**：世界模型判定相关性后产出新版本；冲突并存；旧版本只读留档。
5. **拿主意**：控制环在契约范围内签发意图（"点击 XX"）——只带目标提示，不带授权。
6. **锁定目标**：效果边界把"想点的那个"绑定到当前世界观版本的具体控件（绑定即钉死版本）。
7. **安检裁决**：三关——够不够新（新鲜度）？在契约允许清单内吗？有无未解冲突？全过才形成授权。
8. **放行执行**：闸门只执行判决：先登台账，再降级为设备可执行的目标（坐标/原生键），落向真实屏幕。
9. **回看验证**：**必须**重新观察（可为轻量局部观察）→ 并入世界观 → 安检确认"预期改变真的发生"。
10. **交卷**：全部义务有证据支撑 → 终局证明（四分类）→ 一次性结果信封 → 大脑做满意度评价（只评不改事实）。

### 5.2 失败剧场（本系统设计密度最高的地方）

| 场景 | 系统行为 | 对应失败模式 |
|---|---|---|
| 目标歧义（屏幕上有两个"确定"） | 绑定拒绝，后续链路全部短路，**零副作用**；回到第 5 步换方案 | 治 F1 |
| 世界观过期（页面已翻走） | 裁决拒绝"不够新"；注意：拒绝的是**授权**，不销毁绑定对象 | 治 F1/F2 |
| 执行结果未知（驱动超时） | 进入"未知"态：**禁止盲发**，先重新观察/对账，再由合法决策路径定夺 | 治 F2 |
| 证据不足 | 不生成"完成证明"：保持非终局、诚实标注未知——**绝不装成功也绝不装失败** | 治 F2 |
| 危险/越权动作 | 裁决关（契约红线）拒绝；高权限动作预留一次性细粒度授权（Grant，路线图项） | 治 F3 |

### 5.3 串行验证屏障

> **上一个动作的验证义务清偿之前，系统在结构上禁止发出下一个现实动作。**

批量点击、隐式重试、拿回执提前放行——不是"不推荐"，是在架构层**不存在路径**。这是"慢一点但敢签字"与"快一点但不敢用"的分水岭，也是我们最愿意被挑战的一条设计。

## 6. 生命周期与可审计性

### 6.1 生命周期

```
会话 Session ─▶ 目标 Goal ─▶ 契约 Contract ─▶ 运行 Run ─▶ 结果 Outcome ─▶ 评价 Evaluation
（关联根）      （大脑拥有）  （范围·红线·验收, （合法激活后     （一次性信封,    （大脑打分,
                              版本化）          内核自驱）       附证据清单）     不回改事实）
                                └── Run 内部: 观察→决策→行动→验证 循环 N 次 ──┘
```

终局之后：投递闸门**永久关闭**——迟到的事件、回调、绑定请求一律拒绝。所谓"僵尸运行"（terminal 之后还在偷偷动设备）在这个架构里**没有结构通道**。

### 6.2 可审计性（客户最关心的一页）

三个"敢上线"前提，逐条对应工件：

| 前提 | 机制 | 工件 |
|---|---|---|
| **出事能查** | 每个动作留完整证据链：看到什么→凭什么判→执行了什么→验证了什么 | append-only 执行台账 + 证据记录 |
| **结果能签** | 完成判定=证据支撑的义务清单，不是模型话术 | 交卷信封（义务+证据引用+未决项） |
| **两次能比** | 报告确定性生成、字节级可比 | Run Report 四层粒度：需求→效果达成→组件→证据索引 |

## 7. 工程可信度

### 7.1 能力集：可扩展、可替换、可管理

- 观察侧（感知快/慢/层级、定位候选）、行动侧（设备驱动）、支撑侧（模型管理等）全部是**类型化能力插件**；感知服务是跨进程的 Python 服务（黑盒、可独立升级、可换实现）。
- 替换模型/算法/驱动，只改变质量、成本、延迟——六域权威链**零改动**。这是"组件可替换契约"的结构承诺。

- **可扩展**：新能力按正式的接入开发协议入集（实现协议接口 + 注册 + 验收）；扩展发生在缝上，核心零修改。
- **可管理**：注册按信任域分立；任务内绑定、任务结束即关闭；健康聚合、降级与关闭受生命周期治理；能力身份内容寻址、可版本追溯。

### 7.2 可测试：同一套真件可仿真

- 产品宿主与仿真宿主装配**同一个**运行时工件——仿真不是另一套代码，行为变更两侧同受影响。
- 录制 → 封存（防篡改校验） → 确定性回放：两次运行 digest 一致；场景是证据派生的 stimulus，**Trace 永远不是命令**。
- 这直接治 F4（不可复现）：自动化测试可以对"智能系统"做回归了。

### 7.3 诚实的现状台账（差异化信任牌）

别的团队给你看完成了什么；我们把**还没完成的也标给你看**——每条协议边都有四态状态：verified（有可复现证据）/ known gap（边界已定、实现未齐）/ deferred（等真实需求触发）/ placeholder（占位）。

| 已验证（进程内主链） | 已知缺口（known gap） | 显式暂缓（deferred，无真实需求不预造） |
|---|---|---|
| 观察/行动/终局三条流水线语义 | 跨进程激活的持久身份 | 记忆系统（占位） |
| 三权分立 + 串行验证屏障 | 观察来源（origin）独立字段 | 多目标/多运行/并行 |
| 交卷信封 exactly-once | 完整跨进程恢复 | 取消/暂停/恢复词汇 |
| 确定性回放仿真 | —— | 跨主机意图凭证 |

> 讲法提示：这一页反着讲——"连没做什么都有台账"本身就是工程成熟度证明。业界开发者听众吃这一套；客户听众得到的是"承诺可核验"。

### 7.4 记忆系统与三个自我优化循环

**记忆系统的设计边界**（语义已冻结，实现为显式占位）：

| 唯一拥有 | 永不拥有 |
|---|---|
| 持久记忆记录、记忆溯源、保留策略（retention）、召回（recall）产出 | 证据准入、世界观、运行状态、意图、授权、效果或终局判定 |

核心纪律：**recall 只提供先验/假设/历史参考，永不单独建立当前世界判断**——历史
证据引用保持历史身份，当前判断仍需新鲜证据。买到：**记忆让系统变聪明，但污染
不了现实**。

系统有三个层次的优化循环（自我驱动程度递减、落地程度递增）：

```
                    ┌────────────────────────────────────────────┐
                    │            一次 Run 的生命周期              │
                    └──────┬──────────────────────┬──────────────┘
                           │                      │
     ① 经验循环（设计冻结 · 实现占位）     ② 测试资产循环（已落地）
                           │                      │
        交卷信封 + 评价 ──▶ Memory 持久化         运行 Trace ──封存──▶ 场景库
                           │                      │
        下次 Run 的 Recall ─▶ 先验/假设/          确定性回放回归（digest 一致）：
        观察策略参考（非证据）                     新版本 = 旧场景全绿
                           │
     ③ 配置演进循环（人工在环 · 已落地）
        Profile/Skill/Prompt 版本化 + hash ──Conformance 验收──▶ 下次运行生效
```

- **① 经验循环**：运行结论沉淀为记忆，下次以先验形式召回——影响假设与观察策
  略，不影响证据与裁决。语义已冻结（协议边 P20/P21），实现等真实需求触发。
- **② 测试资产循环**：每次真实运行产出 Trace → 封存校验 → 派生不可变回放场景
  → 进场景库做确定性回归。跑得越多、回归网越密——**运行本身在生成测试资产**，
  这是当前已具备的自我强化。
- **③ 配置演进循环**：Skill/Prompt/模型升级走版本化装配 + C1–C11 conformance
  验收后生效——人工在环、机器验收。

> 讲法提示：对客户讲②（越用越可靠）与③（升级有验收门）；对开发者讲①的边界
> 设计——"recall 永不当证据"是本系统独有的记忆安全边界。

## 8. 当前落地与能力边界

**已落地场景**：车机 Android 设置菜单的覆盖遍历测试——真实设备、真实感知服务（YOLO+OCR）、真实驱动（adb）、完整证据闭环；产品线运行于 DSH 宿主，仿真线运行于 Codex 宿主。

**当前边界**（与优势同等重要，主动说清）：

- 单领域：当前是 UI 领域运行时（第二个领域出现时按证据提取抽象，不预造通用层）；
- 基数 1:1:1：一次会话一个目标一次运行；
- 记忆与跨会话经验复用：占位未实现；
- 生产就绪度（安全审计/运维/升级证据）：路线图后段，不提前宣称。

## 9. 常见问题（Q&A 底稿）

| 问题 | 回答骨架 |
|---|---|
| 和 Playwright/Appium 什么关系？ | 它们是"手"（驱动器），我们是 脑+神经系统+手 的完整执行系统；驱动层可复用它们 |
| 和 computer-use 类 Agent 的区别？ | 不拼模型拼架构：证据层/裁决层/验证义务/终局证明是结构构件，不依赖模型自觉 |
| 安全怎么保证？ | 三权分立 + fail-closed + 契约红线；高权限动作走一次性细粒度授权（路线图） |
| 串行验证会不会太慢？ | 验证观察可为轻量局部信号（非全屏重析）；用"慢一点"换"敢签字"；关键路径延迟在持续度量 |
| 出错怎么恢复？ | 恢复必须重入正常闭环（重新观察→重新并入→再决策），禁盲重试；台账支持对账与补偿 |
| 怎么集成进现有流水线？ | HTTP 运行面 + 只读查询契约（语言无关 schema）+ 确定性 Run Report 工件 |
| 会有记忆/学习能力吗？ | 设计了三个优化循环：**经验循环**（运行结论→记忆→下次当先验；实现占位，等真实需求触发）、**测试资产循环**（已落地：Trace→场景库→确定性回放，越跑回归网越密）、**配置演进循环**（已落地：版本化+conformance 验收）。核心边界：recall 永不单独当作现实——记忆让系统变聪明，污染不了现实（详见 §7.4） |

## 附：术语速查（十词）

| 术语 | 一句话 |
|---|---|
| Observation 观察提案 | 感知的原始申报；登记合格后才叫证据 |
| Evidence 证据 | 登记在册、可引用、带来源的依据；只回答"依据什么" |
| WorldBelief 世界观 | 当前对屏幕的判断；版本化、冲突并存 |
| Intent 意图 | 控制环签发的"想做什么"；非命令非授权 |
| Binding 绑定 | 把"想点的那个"钉到特定世界观版本的具体控件 |
| Judgment 裁决 | 安检对（意图+绑定+世界观版本）三件套的一次性判定 |
| Receipt 回执 | 指令送达留痕；只证明"发了"，不证明"成了" |
| Verified Effect 已验证效果 | 动手后重新观察证实世界真的变了 |
| Outcome Proof 终局证明 | 义务是否有足够证据支撑的最终判定（成功/失败/安全停/升级 四分类） |
| Fail-closed 失败即关门 | 任何不确定一律安全拒绝，绝不"先试试" |
