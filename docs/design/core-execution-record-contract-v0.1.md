# Core 执行记录契约 v0.1（设计评审稿）

> Status: `DESIGN / APPROVED`  
> Change: `CORE-009`  
> Authority: `NONE`  
> Scope: 可靠执行记录契约设计；不包含 Runtime、Trace、存储实现。

## 1. 目的与非目标

本契约为 `Effect` 的执行尝试提供可恢复的记录保证。它保留 `Attempt` 的产品语义，
但不预设独立类、独立数据库或新的 Core 顶层记录。

本契约不把普通诊断 Trace 变成恢复依据，也不把 Receipt 或 AttemptReport 变成外部世界
结果证明。World 结果仍必须经过 Evidence / Claim 路径判断。

## 2. Owner 与 Authority

| 语义 | 责任方 | 说明 |
|---|---|---|
| Attempt 语义 | Core 契约 | 定义一次尝试必须能表达什么，不决定物理存储 |
| 准备登记、发送关联、回执关联 | Runtime / Effect Boundary | 必须在发送前保留准备信息，发送后追加过程和反馈 |
| 目标绑定与固定依据 | Effect Boundary | 绑定依据固定；当前 World 改变不改写历史绑定 |
| 诊断 span、耗时、丢弃计数 | Trace | 非权威观测；可引用 Attempt/Receipt，但不替代执行源 |
| 外部世界判断 | Evidence Ledger / World Model | Receipt/AttemptReport 不能直接建立完成或成功 |

物理上可以复用现有记录或存储；逻辑上只能有一个可写的执行事实来源。Trace 与
Runtime 不能各自独立改写同一项尝试结论。

## 3. Attempt 的最小语义

一次 Attempt 至少要能稳定还原：

1. Attempt 身份及其所属 Effect；
2. 当次请求的固定快照或可验证还原引用；
3. 当次 TargetBinding 及其固定依据；
4. 执行端与 capability 关联；候选建档可以暂缺，但进入发送前必须能唯一还原实际执行端；
5. 授权/准入依据关联；是否需要人工确认可由已接纳、版本化的操作或用途契约决定，但不能
   由未受信调用方自行声明“不依赖”；
6. 发送前准备已登记这一事实；
7. 发送过程、提交确认、无 Receipt 的未决状态和迟到反馈的关联；
8. 重试、依赖或补偿关系；这些是执行组织关系，不自动证明外部因果。

这些信息表达“系统准备或尝试了什么”，不表达“外部目标已经完成”。未知必须保持未知。

同一次实际提交采用的请求、参数、目标绑定、执行端、准入依据和允许的转换规则必须能作为
完整、可还原的一组信息发布。任何一项发生变化，都必须重新固定并重新核验，不能只修改
内存对象后继续发送。

## 4. 三条状态轴，不使用万能生命周期

执行记录应分别保留以下维度；具体枚举不在本契约冻结：

| 维度 | 示例问题 |
|---|---|
| 准备/提交进展 | 是否登记准备？是否开始提交？传输层是否接受？ |
| 外部执行判断 | 外部执行未观察、待确认、已确认失败、结果未知？ |
| 协调状态 | 是否仍需查询、对账、补偿或责任处理？ |

一条轴的值不能推导另一条轴。提交确认不等于外部完成，外部未知不等于未发送。外部执行
判断和协调状态可以形成视图，但必须引用对应的 Evidence/Claim、条款和规则依据，不能成为
与 World 或责任评价竞争的独立可写结论。

## 5. 记录产生与存储选择

允许两种实现形态：

```text
方案 A：Runtime 保存满足本契约的 Attempt 记录

方案 B：Runtime 保存满足本契约的执行源记录
        ↓ 按稳定的投影规则生成 Attempt view
```

方案 B 只有在执行源记录能提供同等保证时成立。必须能还原过去采用的投影规则版本和输入，
不能用升级后的投影结果冒充历史记录。普通诊断 Trace 不满足默认条件，除非另有契约证明
其完整留存、不可静默丢失、发送前登记和恢复可读性。

## 6. 必须覆盖的时序

### 6.1 发送前准备

先登记 Attempt、Effect、固定请求、Binding、依据、实际执行端和准入关联。Runtime 必须
取得“准备记录已可靠提交”的明确结果，且该记录能在本契约声明的故障范围内恢复读取。
仅创建内存对象或发起异步写入不算提交完成。该登记只表示准备已留存，不表示请求已经发送。

准备记录提交结果有三类：

- **成功**：允许进入后续准入与发送流程，不等于已授权或已发送；
- **失败**：不得继续调用 driver；
- **未知**：沿原 Attempt/提交关联查询或协调，不得当作成功，也不得换身份后直接发送。

恢复器必须能够在不知道 Attempt ID 时，按声明的恢复范围枚举和发现未决准备记录；不能只
提供“知道 ID 才能查”的接口。本契约第一版只要求覆盖单执行路径、进程崩溃与重启，不承诺
磁盘损坏或跨节点接管。

### 6.2 提交确认

提交过程和提交确认追加到同一 Attempt。这里的确认必须区分：本地记录提交成功、请求交给
driver、传输层接受和外部业务接受。确认只能说明对应层的事实，不能自动升级为外部世界结果。
实际提交给执行端的内容必须与已核验的操作、参数、目标绑定、执行端、准入依据和允许转换
规则一致；不一致时停止发送并重新固定核验。

### 6.3 无 Receipt

如果 driver 调用后进程崩溃或没有回执，Attempt 仍必须存在，外部执行状态为 Unknown 或
等价未决状态。没有 Receipt 且缺少其他充分结果依据时保持未知；恢复不得盲目重发，应先
查询、重新观察或按契约协调。满足有效授权和操作契约的安全重试条件后，才可登记新的外部
投递 Attempt；无 Receipt 不永久等于未知，也不等于失败。

### 6.4 未知结果协调

查询、对账、等待和责任处理都引用原 Attempt。对同一逻辑干预的再次外部投递登记新的
Attempt；本地准备记录的提交/查询重试仍保持原 Attempt 关联，不能因为提交确认丢失就自动
创建新的外部投递 Attempt。改变逻辑目标、对象、金额或操作含义时建立新的 Effect；补偿
属于新的 Effect，并保留与被补偿 Effect 的关联，补偿自己的投递再通过 Attempt 表达。

### 6.5 迟到反馈

迟到 Receipt 或其他反馈通过稳定的 Attempt/提交关联追加或更正。更正通过新增记录及关联
表达，不覆盖原请求、原绑定、原始回执或历史评价。反馈关联不明确时保留为待关联反馈，
不得按当前配置、最新 Binding 或最新 Trace 重新猜测目标。

## 7. 现有仓库复用审计结论

- `EffectBoundary.BindingLog` 能保留绑定判定，但不是完整的发送前 Attempt 记录。
- `EffectBoundary.ReceiptLog` 是发送后 Receipt 留痕；当前 Receipt 在 driver 返回后才追加。
- `ExportAttemptEvidence` 和 `ExportTransitionContext` 以 Receipt 为输入，不能覆盖无 Receipt
  的准备或未知尝试。
- `RunTraceArtifact` 是非权威诊断投影；Trace 可禁用，异步 writer 可显式丢弃记录。

因此当前实现可以复用其关联标识和部分记录，但尚不能证明已经满足本契约。此结论不是
迁移方案，也不授权修改实现。

## 8. 验收计划（本轮只提交计划）

### 合同检查

- 检查 Attempt 语义、来源、存储/投影和 Trace 权威边界是否分开；
- 检查请求快照、Binding basis、执行端和授权依据是否能固定还原；
- 检查缺失字段只局部阻塞，不把未知变成失败/未发送/成功。

### 场景验证计划

1. Trace 开启和关闭两条路径对比；
2. 准备记录尚未可靠提交时崩溃；
3. 准备记录已提交、尚未进入发送边界时崩溃；
4. 准备提交失败或结果未知时不得进入 driver 调用；
5. driver 已调用但 Receipt 丢失；
6. Receipt 迟到；
7. Unknown 查询后确认成功/失败；
8. 请求、执行端、Binding 依据与已核验集合不一致时停止发送；
9. 同一准备提交的本地重试保持原 Attempt，外部投递重试生成新 Attempt；
10. 重试与补偿层次对照：重试沿同一 Effect，补偿建立新 Effect 和自己的 Attempt；
11. 旧 Binding 过期后不得跟随最新定位；
12. Trace 队列丢弃时仍能读取可靠执行源。

本轮不执行这些场景，不宣称恢复能力已通过；实现前须先评审本契约和复用边界。
