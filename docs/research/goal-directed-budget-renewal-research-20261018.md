# 目标推进与预算续额策略研究

日期：2026-10-18。状态：Research / Authority: NONE。只读检查与讨论输入；不是已批准协议，不修改产品代码、预算配置或 ADR。采用 research / codebase-design；本 Host 缺少 Codex 模型绑定，后台研究路由为 ROUTING_UNAVAILABLE，由 Leader Direct 完成。

## 1. 研究问题与结论

Owner 关注的是是否沿着预期和目标推进。循环只是失败的一种：持续打开新页面、成功执行新动作，也可能与任务无关；必要回退、排除错误假设或为目标获取证据，也可能有价值。

建议把两个决定分开：先以目标及证据评估“应继续、需重规划、需补证据、应停止”，再决定本段预算。20%可以作为默认续额批量，不能证明方向正确。在本次查阅的一手资料中，未发现20%是通用标准。

## 3. 当前代码真正做了什么

调用链：Product budget config → SettingsCoverageRunner 的 AgentPlanPolicy → KernelRunDriver 开窗口 → UniAgent 返回 renewal → ValidateRenewal → 轻记账授额；Settings 的停滞信号在 Host 侧独立形成。

- `src/UniClaw.Kernel/Runtime/ConsultationTypes.cs:68`：申请只有 `AdditionalSteps`、`AdditionalRounds`、可选 `Justification`。没有阶段、评估基点或可核验依据引用。
- `src/UniClaw.Kernel/Runtime/KernelRunDriver.cs:1102`：审批只核验通道、窗口、非负/非空与累计上限。没有检查目标相关性或自上次授额后的实际推进。
- 同文件 Defer 分支：任意续额获批都可重启已耗尽的 Defer 链，未区分新授的是动作步数还是咨询轮次。续额会补资源，但不能据此证明应继续等同一观察。
- Director 的停滞后备依据 `(StepsVerified, frontier数量)`；Runner 的中断依据 `(entered/reached数量, frontier数量)`。后者能避开“清障反复成功”的部分假进展，但数量仍缺少目标身份及关联关系，且两套口径没有形成统一续额依据。
- Prompt 已要求 useful progress；这属于模型指导，没有成为规则侧可查验的条件。当前窗口没有直接给20%默认值、进度检查点及最近续额审批结果。
- Act/NoAction 的 renewal 在 proposal 内，Defer 在 payload 根层；Skip/Policy 不携带同样申请。之前错层字段的真实错误已证明形状差异有调用成本。字段路径统一可在后续协议版本讨论，不把旧结构在 adapter 中悄悄搬移。
- Act 先按当前预算验证步骤数，再处理续额；预算已为0时，不能假定“Act同时申请额度”就能救活。应提前开窗，并明确同一次决定的审批/采纳顺序。

## 5. 建议的判断模型

评估输入以原 Goal / accepted Contract、当前阶段预期、上次检查点、真实结果及未完成义务为准。不能以是否严格遵守最初计划判对错：计划可以修订，目标和授权不能被模型静默改写。

| 当前情况 | 续额与控制动作建议 |
|---|---|
| 有新证据证明阶段目标推进，剩余工作仍在授权范围 | 继续执行；窗口开启时默认申请初始额度20%，到下一检查点再评估。 |
| 目标相关探索，尚未完成阶段目标，但已消除具体未知或验证必要前置条件 | 可有限继续；写清下一段要验证的判断及成功/失败出口。新页面或新日志本身不足以支持此项。 |
| 与预期不符，存在可说明的新策略 | 先重规划；为恢复/验证新策略给有界机会，不能重置累计无进展历史。 |
| 动作持续成功，却没有与目标相关的变化；或探索已偏离目标 | 不按正常推进续额；重新定位方向，无法恢复则停止/升级。 |
| 缺少可信证据，方向无法判断 | 申明 Unknown，允许必要的有界取证，不能伪造进度或直接宣称任务完成。 |
| 目标已满足、授权冲突、不可恢复或资源硬顶已到 | 分别进入已验证完成、受阻或预算耗尽出口。完成由现有 Assurance/Outcome 机制判定。 |

“探索”“恢复”“正常推进”是申请用途与评估分类建议，不是新增 Run 生命周期或 Capability。不能仅靠每轮换一个 nextMilestone 或措辞重置失败历史。

## 6. 申请结构：金额之外要说明什么

先讨论语义，暂不冻结字段名或 JSON Schema。最小候选如下：

| 数据 | 来源/作用 |
|---|---|
| 当前目标、阶段与检查点引用 | Runtime提供合法引用；绑定当前Run/Contract，避免改目标或复用陈旧理由。 |
| 自上次授额后的变化与证据引用 | Agent说明与目标的关系；规则核对证据存在、时效、归属和已验证事实。Agent不重复填权威计数或自定progress=true作为批准依据。 |
| 剩余工作、下一段预期及其验收方式 | 说明这笔额度将用于什么，下一次如何核对；这是假设性承诺，未完成前不能计入成果。 |
| 用途：推进/探索/恢复 | 采用不同的有界继续策略；未推进时必须说明为何新尝试有根据。 |
| 追加动作数、咨询数及简要理由 | 默认20%由Runtime按初始额度计算并提供建议；按需要维度申请，最终额度截断。20%是批量建议，具体比例仍需任务数据验证。 |

继续复用当前 decisionId / Run 关联，不为申请发明新的身份系统。目标、阶段引用若现有实现还没有可用标识，必须先确认真实 buyer 与已有 obligation/trace 引用能否表达，不能造无消费者的新 registry。

上下文还应提供：建议续额、各维剩余可授额度、此次开窗原因、上次审批结果。工具接收 proposal 不等于规则已授额，后续咨询必须能分清。应按“自上次获批后的新增依据”检查，不能用同一条旧成果反复取得正常推进额度。

字段统一是否迁移到公共决策信封，应在确认 Skip/Policy 等真实续额消费者后另定协议版本；当前研究不引入兼容别名或双写。

## 7. 职责与授权边界

- UniAgent结合目标、计划假设及证据解释方向，提出继续/重规划/停止与续额量；这是语义评估，不是自授预算。
- Runtime/Host投影事实及已有义务；Kernel规则核验关联、已有可判定条件、资源上限和Effect权限。Settings语义不得硬编码进通用Kernel。
- 已有Run Progress记录执行义务，Assurance仍拥有验证及Outcome judgment。无需把每次申请写成新的canonical Run transition或建立第二个Goal Evaluation系统。
- 本仓架构基线明确：动作数、观察数、coverage、provider成功不能单独成为progress truth；Plan是可被证据推翻的假设；coverage/no-progress不单独证明objective satisfied。建议沿现有责任补齐事实与申请，不另造总控模块。
- ADR-0050仍要求有限HardCap。用户所说“正确推进就不停续”，在当前约束下可解释为窗口开启且仍有合格依据时持续授额，直到完成或既定硬顶；若希望正确推进时自动提升硬顶，这是另一个明确的资源授权决定，不能通过重开Run绕过。

## 8. 下一步讨论与验收样例

建议先确定“对目标有价值”的口径，再冻结字段与比例。首版验收至少覆盖：阶段成果推进应续；必要探索应有界继续；必要回退不误杀；动作成功但跑偏不续；重复/交替/同义改写的空转不能续；陈旧/虚构证据不采纳；同一成果不能重复授额；纯步数续额不重置咨询等待；重规划不能清空历史；剩余空间不足20%时截断；达到HardCap即使仍有进展也如实报告资源边界。

## 9. 用连续 overview 判断全遍历与本笔续额

Owner 进一步提出：从overview应能看到历史进展及本次续额的进展，连续多轮overview应足以支持是否续额的判断。这可作为本场景的主要消费要求。

### 9.1 当前实际缺口

当前产品执行代码没有名为overview的统一事实投影。已有Progress计数、Heartbeat/CasePacket、Coverage账本与最终报告可以提供部分材料，但分散在不同位置。应先定义消费者需要的overview语义，再复用现有投影与owner数据，不因此新建权威状态。

正式全遍历decision100时85步已派发且验证成功，decision108时91步已派发且验证成功；最近步骤包含Modify system settings的重入和Navigate up。增加6次成功动作不能直接解释目标推进量。最终报告仍是一级3/7、二级8/8、scroll-discovered 0/1，尚有嵌套待办。因此单个成功步数或整体要求比例不足以表达遍历方向。

该run的109条consult-bridge记录中12条有Heartbeat；这是Director装饰前的上下文记录，不能当作模型完整实际输入。Director还会注入当前directive、局部视图和近3周期的route/verified/frontier事实，但没有统一的累计覆盖、本笔续额基点与预期对照总览。

### 9.2 每份overview至少回答六个问题

| 视角 | 内容 | 判断作用 |
|---|---|---|
| 目标与阶段 | 同一Goal/Contract及范围版本；当前分支/任务；本阶段预期和下一检查点 | 确认当前路径仍服务原目标，不因换计划而换目标。 |
| 累计历史 | 已验证的不同目标及身份、已发现待办、未决、跳过及理由、尚未探索的范围 | 展示真实积累；重复返回不变成新增覆盖，跳过保留为独立事实。 |
| 与上一轮相比 | 新验证目标、新获相关证据、已排除假设、失败/回退、待办集合变化及引用 | 支持连续overview辨别方向；不仅比较数量。 |
| 本笔续额 | 申请/批准/拒绝状态、实际追加量、批准时检查点、此后消耗、约定预期及已实现/未实现结果 | 看清本笔资源花在哪里、是否兑现。未授额前明确“尚无本笔”，初始额度单独显示。 |
| 当前局面 | 当前页面/分支、最近预期与实际、阻碍、不确定性、必要恢复路径 | 解释短期无新增覆盖是否合理，以及是否需要重规划。 |
| 下一段 | 仍需完成什么、拟采取的路径、预期得到何种证据、何时检查、剩余与可授预算 | 让继续执行有可核对的目的；推荐结论必须与底层事实区分。 |

全树尚未发现时，已发现目标数量只能作为已知范围分母；新增发现可能令已知覆盖比例下降。这不一定倒退，不能因为百分比没涨就否决相关探索。跳过或判定不可达可减少未决工作，但不能静默标为成功访问；最终是否满足任务仍按原验收要求判断。

### 9.3 多轮overview如何形成判断

保留两个比较基点：上一overview与最近一次获批续额时的overview。既看短期变化，也看整笔预算的累计效果；中途重规划不能清掉旧消耗和未实现预期。

- 目标相关的验证成果或必要前置条件持续增加，路径在范围内，且仍有待办：支持正常续额。
- 正在必要返回或取证：依据阶段路径及预定检查点判断，允许有限继续；不要求每一步都新增覆盖。
- 连续动作成功但目标集合/相关证据无改善，或本笔额度接近用完而预期始终未实现：重规划或拒绝继续为同一方案续额。
- 多轮内容仅换描述、换目标名却未出现可核验的新依据：不能因此重置停滞记录。
- 总览缺证据、归属不清或与实际矛盾：返回Unknown并按引用查详情；摘要不能提供绝对的正确路径证明。

初始建议按阶段检查点及若干overview形成的窗口评估，不直接冻结“连续3轮无新增目标即失败”一类阈值；正常深层进入与返回可能需要多轮。

### 9.5 对申请结构的简化

如果overview已含上述事实和证据目录，申请不需要再复制一遍历史。候选语义可收敛为：引用当前overview/获批检查点、指出下一阶段预期、申请步数/咨询量及用途。方向判断使用多轮同源overview；规则核验引用与可判定条件。

overview作为每次咨询前、UI和审计可共同消费的只读投影，关联现有Run/Decision/事件cutoff。历史保留累计事实及上次授额基点，模型上下文只携带近期有界增量和可按需检索的引用，不把整段运行历史逐轮重传。无需另建overview权威账本、独立续额大脑或第二套Run生命周期。

后续若实现，应验证overview的重放一致性、同名目标身份、scope变化、grant基点与事实新鲜度；模型写出的总结本身不能替代底层验证事实。
