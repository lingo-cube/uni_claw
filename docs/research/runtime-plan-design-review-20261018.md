# RUNTIME-PLAN-001 产品执行 Plan 设计复核：有限前瞻、技能层级与行为树

状态：Research / Authority: NONE  
研究日期：2026-10-18  
范围：对照当前 [proposal.md](../../changes/RUNTIME-PLAN-001/proposal.md) 提出有限、可操作的改进建议；不修改主方案，不构成 Owner 决定或实现授权。

## 结论先行

proposal 的整体方向与可见业界机制相容：计划可在高层表达目标/可组合技能，运行时根据当前状态有限展开，动作后取得反馈再继续。当前最值得收紧的是语义边界，不是换成完整 BehaviorTree（BT）或学习型技能库。首版建议明确粗阶段、当前可执行段、单步动作三层；给动作和段落补上可验证的结果/失败/未知及续行约定；把局部展开上限和阶段检查点写成不同概念；验收中增加固定短 Plan 与规则 Plan 的对照。复用技能库和完整 BT 语法可以延期。

以下四项为本轮新核的一手资料，集中在与设计直接相关的机制，不重复既有 Harness 综述。事实与对 UniClaw 的迁移判断分开陈述。

## 一手资料及其支持范围

| 来源 | 来源直接支持的机制 | 限制 / 对本方案的推断 |
|---|---|---|
| **滚动有限前瞻（RHC/MPC）**：Mattingley、Wang、Boyd，2010 论文稿 / 2011 IEEE 发表，[作者论文](https://web.stanford.edu/~boyd/papers/pdf/code_gen_rhc.pdf) | 在每个离散时点，以当前可得状态估计求解一个有限未来窗口的受约束动作序列，应用当前输入，下一时点基于新测量重算。作者解释该法使用实时反馈，但每步重算也带来优化成本。 | 这是已知动力学和数值优化控制问题，不是语言模型，也不能直接证明手机 UI 使用短 Plan 会省调用。可迁移的是“前瞻窗口 + 当前边界执行 + 以新状态续算”的边界思想；不要移植其最优性/稳定性保证。窗口长度与目标函数如何取舍仍需实测。 |
| **SayCan 技能选择**：Ahn 等，2022，[作者论文](https://arxiv.org/abs/2204.01691) | 对预先提供的低层技能，用语言模型估计“是否有助目标”，用当前状态的 affordance/value function 估计“能否执行”，组合分数选一个技能；执行后更新环境状态并再次选技能。论文测试多步移动操作任务。 | 这能说明“层级目标 + 有界技能集合 + 当前状态可行性”可组成循环，不必将整条动作序列全预知。它依赖训练/定义好的机器人 skills 和 value functions；UniClaw 的场景规则/Guard 与学习型 affordance 不是同物。论文实验也显示计划成功与实际执行成功有差距，不能把较高计划质量当成完成证明。 |
| **Behavior Trees（BT）**：Colledanchise、Ögren，[作者专著预印本](https://arxiv.org/abs/1709.00084)，arXiv条目专著引用为2018 | BT 用有限种控制节点组合层级任务。经典 Sequence 顺序 tick 子节点，子节点 Failure/Running 会停止向后推进；Fallback 按优先级逐一尝试；Action/Condition 返回状态；持续 tick 和重查条件可在前置状态变化时中止当前行为并切换分支。 | 这为“条件、顺序、备选与可反应执行”提供已定义语义；同时作者指出 BT 引擎实施可能复杂、闭环检查条件可能昂贵，某些环境下简单开环执行足够。其经典 Action/Condition 是 Success/Failure/Running，不能无损映射 UniClaw 的“未知”三态和 Effect 在途屏障。应只借鉴小子集，除非已知买方证据要求完整 BT。 |
| **Voyager 可组合技能与执行反馈**：Wang 等，2023，[作者论文](https://arxiv.org/abs/2305.16291) | Minecraft agent 将已完成且验证的可执行代码程序存入技能库、检索相关技能用于新任务；执行时把环境反馈、解释器错误、状态和自我验证纳入下一轮生成/修正，最多迭代若干轮，确认完成后才入库。 | 说明技能组合和反馈可支持长任务，但这是结构化模拟世界，技能直接是代码且由专门模拟器/验证器支撑。不可据此推断应让手机 Agent 生成/运行代码、自动学习在线规则或用模型自评取代 Assurance。可先复用静态 typed 操作，不建设在线技能学习平台。 |

## 对当前 proposal 的具体审查

proposal §6.1–6.3 已写明阶段目标、当前规则/操作、逐项 grounding/验证和局部工作量；§7 把动态候选放进真实遍历例子；§8 有版本、游标和恢复约束。这些内容已经覆盖了大部分“短步闭环”所需责任。以下建议是把不变量说得更可判定，不表示要求新增 DTO 或改变 D1–D9。

1. **把前瞻范围与展开工作预算拆成两个维度。** §6.2/§6.3 已有检查点和 `local expansion work` 上限，但目前“有限段/一次 Plan decision/段落耗尽”容易被读成同一个数字。建议在 §6.1 或 §6.2 明确：阶段目标可较长；当前可执行段受规则适用范围和检查点约束；每一动作都必须使用当前事实重新校验。前瞻范围决定承诺执行到哪里，展开工作量界限防止观察/条件求值/未知反复空转，两者不等于总任务额度，也不强制另加通用动作数硬顶。到局部边界只表示yield/checkpoint，不代表全任务完成；数值若有需要须由买方基线确定。RHC提供的是窗口滚动思想，不提供适用于LLM/手机的最优窗口长度。
2. **为操作结果补一张最小续行表。** §6.2 已提到动作及验证预期，§6.3 已记录结果，§8 已区分中断和预算复核。建议补清 `verified-success`、`verified-not-achieved`、`unknown/unobserved`、`execution-failed/in-flight` 的语义分别是推进、按规则转备选、补证/暂停咨询、等待原 Effect 对账；不把 tool 返回、点击派发或模型自报“成功”视为后置条件成立。BT 的 Action Result 给出运行状态的例子，但 UniClaw 需要保留更精细的未知和在途约束。首版只规定这些转移，不必设计任意恢复 DSL。
3. **将“层级”限定为语义层级，先不建通用技能市场。** §6.1 的 Owner 表、§6.2 的有界组合、§7 的场景遍历已具备“目标阶段 → 规则/可组合操作 → 当前具体动作”的层次。建议在 §6.1 加一句硬边界：Agent 引用/组合的是已经声明且可校验的场景操作及有限规则；Runtime 不把 Agent 新写的代码或未注册的自然语言动作当 skill。可验证的已知多步段可作为首版复用形状；自动归纳技能、embedding 检索、跨运行学习和在线覆盖技能留到后续，有明确重复任务证据及静态验证/版本/撤销机制再研究。SayCan 和 Voyager 的 skill contract 由它们自己的低层接口/验证条件支撑，不能等同于当前 Capability registry。
4. **只借 BT 的控制流骨架，不引入完整 tick 引擎。** 首版可用序列、有限选择/备选、已声明条件三个概念解释 §6.2，不支持并行、任意 decorator、tick 频率、通用中断树或任意递归。当前有序步骤逐项执行；条件在每个动作前按新鲜事实求值；`unknown` 不被压成 `failure/false`；只有当前动作完成或对账后才能切换分支。这保留 BT 的反应性动机，同时不让“重新 tick”跳过 Control、执行屏障或场景 Guard。只有买方场景证实需要持续监控/抢占，才评估更完整 BT 运行语义。BT 来源特别指出闭环条件检查可能增加成本；成本应进入实测。
5. **把验收对照从二组扩成三组，拆出 Plan 的收益来源。** §10 当前以逐步 Agent 为主比较对象。建议增加同样目标/初态/权限/验证的三组：逐动作 Agent 决策、静态已知路径短 Plan、动态候选/规则 Plan。分别记录 Agent 决策次数、场景条件/观察次数、token/费用、端到端时延、已确认/失败动作、失败后恢复率和是否达成。这样可区分收益来自“把多步预先列出”还是“Runtime 本地规则展开”；也能发现缩减 Agent 调用但把成本转移到慢感知/条件反复检查的情形。一次机器人/游戏论文的执行成绩不替代目标 Android Settings 的同条件结果。

### overview 的一个可选收紧点

§8 的 overview 已要求阶段预期、已验证成果、位置、剩余/未知及下步依据。建议把“目标相关的已验证成果/未满足条件”列为最先展示的部分，待办数量只作辅助字段。不同拆分粒度能任意改变 todo 数量；单纯净减少无法证明沿阶段目标前进。该项可在持久模型之外先作为投影/验收约束，避免过早新增第二份进度事实权威。

## 首版与延期边界

**建议首版保留：**

- 粗阶段目标作为导航和进度锚点，明确它本身不可执行。
- 有界、可组合的既有语义操作；可表达一个有界执行段，不要求预生成完整环境动作树。
- 逐个操作以最新事实重检适用性、策略许可、grounding、Effect 与结果；场景未知值保持独立并沿现有控制链停止/补证/咨询。
- 清楚区分局部动作数、观察/求值工作量和全 Run/预算复核；按来源或 Owner 记录预期、结果及版本位置。
- 对真实 Settings 的固定路径短 Plan 和动态规则 Plan 分别验收，并与逐动作决策比较实际调用/时延/费用/完成率。

**建议延期：**

- 完整 BT 语法和持续 tick/并行执行器；首版只需小型受限组合语义。
- Agent 生成或 Voyager 式自动累积可执行代码 skill、向量检索和跨任务自动泛化。
- 对所有分支/深度建静态完整树、自动证明全局终止，或把“候选集合为空”当完成证明。
- 基于 RHC 类比设定未测定的固定 horizon 数字、成本收益或成功率保证。

## 反例：短 Plan 也可能过期或遗漏必要前置

任务是按规则进入一个已知菜单并读取信息。Plan 说“返回上级页 → 打开条目 X → 读取值”。但上一步返回后，弹出的确认层、网络加载或系统状态改变使 X 不再是当前候选；或者 X 的前置条件实际是先切换 profile。若 Runtime 只检查“Plan 下一行仍存在”，短 Plan 仍会沿旧顺序点击。反过来，若将 BT 的 Fallback 对每个 UI 状态持续重 tick，可能重复枚举/观察，或在 Effect 尚未对账前抢占动作。稳妥原则是：先以当前事实验证 operation precondition；每个 Effect 完成/失败/未知有明确结果边；效果未对账时不推进；只有条件和结果映射落在已声明规则内才继续本地处理。新语义仍交回 Agent。

这是将控制论文、BT 与机器人/模拟环境机制迁移到 proposal 的反例，并非上述来源对 Android UI 的实验发现。

## 本轮不能确认

- 没有证据能给 UniClaw 的最优操作数/horizon 长度、条件重查频率或何时必须调用 Agent 一个固定值。
- SayCan 的 affordance value function 能否对应当前 Settings Guard、候选筛选或 Android accessibility 证据，未获证明；它们不应仅因相似词汇而合并。
- BT 的 condition/action statuses、抢占与 UniClaw 三态判定、ControlIntent、Effect 账本和预算复核之间的精确映射须由协议/代码实现阶段再验证。
- Voyager 的代码技能安全、版本与验证方式不能直接迁移；它的 benchmark 提升不证明本产品需要多 Agent 或自动技能学习。
- 本轮仅对 proposal 与一手资料作设计复核，没有另做源码、协议、设备运行或性能测量；本笔记不把建议写成已接受选择。
