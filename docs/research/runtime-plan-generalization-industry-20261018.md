# 通用执行策略：业界机制对照（RUNTIME-PLAN-001）

状态：Research / Authority: NONE  
研究日期：2026-10-18  
范围：回答“能泛化的任务，为什么要模型一步步下指令？”；仅调研，不修改产品、Change 或 ADR，也不构成接口或实现决定。

## 结论先行

业界确实有“模型/规划器先给出一段可执行策略，运行时按新事实自行推进”的做法；它不等于把所有任务塞进同一条固定规则，也不等于让执行器猜未知界面的语义。

从下列来源可以归纳出三层分工：目标说明想达成什么；动作/条件/恢复组合说明已知能力怎样配合；运行时读取真实状态、检查前置条件和结果，并在策略不再适用时局部修复、重规划或回问模型。这是对来源的归纳，不是所有系统都采用的统一架构；模型的价值可以从“逐点击发令”上移到“为当前任务选择并组合策略”。

对本项目的直接含义是：当前单层 `ForEach` 只证明了一个受限的循环原语，不能证明已经具备上述通用组合能力；但也不应因此直接引入完整行为树、PDDL 求解器或让模型执行任意代码。

## 四条可比路线

| 路线 | 谁给策略 | 运行时怎样继续 | 与本题相同处 | 不能照搬的部分 |
|---|---|---|---|---|
| **Programmatic Tool Calling（PTC）** | 模型写一段调用已注册工具的程序 | 程序可顺序、条件、循环地调用工具；工具结果回到程序，完成后才把最终输出交回模型 | 一次模型决策可覆盖多个工具调用，适合“列出候选→筛选→逐项处理→汇总” | 通用 Python 的权限、终止、资源和审计边界要另建；不适合直接给手机 UI 任意执行代码 |
| **Code as Policies / CodeAct** | 模型为任务组合已有感知、控制 API 和函数 | 程序执行中读取反馈；失败/新信息时可再生成或修订 | 模型生成的是可组合策略，不是固定每步命令 | 研究系统的代码执行环境、API 和评测世界已预设；没有自动理解未知 UI 的保证 |
| **BehaviorTree.CPP / Nav2** | 工程师预先声明条件、动作、顺序、备选、恢复子树 | 持续 tick；条件变化可抢占；失败走恢复并重试主分支 | 条件、循环/重试、子流程、恢复都由运行时根据新状态推进 | 树本身不从自然语言推导语义；完整 tick/并行/抢占语义不能直接压进现有 Run/Effect 边界 |
| **PlanSys2 / PDDL** | 人先建领域动作的前置条件与效果；求解器按当前事实计算行动序列 | 执行器在运行时检查要求，外层控制器可以更新事实/目标后再求新 Plan | 清楚地区分世界事实、目标、动作模型、计划与执行；计划失效可重算 | PDDL 需要可靠、离散的状态模型与动作效果，未知/模糊 UI 不天然满足；不是让 LLM 自动补齐领域语义 |

### 1. PTC：程序代替“每一步再问一次模型”

Anthropic 的官方 PTC 文档明确把工具调用放在模型生成的代码中：代码可串联、循环和按条件调用工具；工具调用暂停程序、把结果返回程序；程序结束后才把结果交回模型。[官方文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling) 与其费用审核示例都属于这种形状：一次策略先枚举人员，再取数据、过滤和汇总，而非每取一条数据都重新让模型选择下一步。[官方工程文章](https://www.anthropic.com/engineering/advanced-tool-use)

这最贴近用户的直觉：模型可以说“对每个当前可进入且许可的菜单，进入、读取、标记、返回；遇到未知或策略未覆盖的页面停止并上报”。但对 UniClaw，更合理的迁移不是开放 Python，而是把可用的**已声明操作、条件、循环、局部变量和退出条件**做成受类型约束、可审计的策略表达。

### 2. Code as Policies / CodeAct：模型组合能力，不逐条操纵

Code as Policies 让模型从自然语言任务生成代码，并在代码中组合已有感知与控制 API、反馈循环和层级函数；论文示例面向机器人任务。[论文](https://arxiv.org/abs/2209.07753) / [项目页](https://code-as-policies.github.io/)。CodeAct 则把可执行 Python 作为统一动作空间，代码执行和观察可在后续多轮中修订。[原始仓库](https://github.com/xingyaoww/code-act)

它们支持的不是“模型一次性猜完整未来”，而是“模型写出可在当前反馈下运行的局部策略”。它们也不证明未知 Settings 页可被自动归类为菜单、开关或安全项；那仍要由观察/grounding、Owner 事实、许可和验证链决定。

### 3. 行为树：运行时按条件推进、重试、恢复

BehaviorTree.CPP 提供顺序、备选、装饰器和子树组合；`ReactiveFallback` 会在前置条件变化时中断正在运行的异步分支。[Fallback 语义](https://www.behaviortree.dev/docs/nodes-library/FallbackNode/)；多个树可通过 `SubTree` 复用。[子树文档](https://www.behaviortree.dev/docs/tutorial-basics/tutorial_05_subtrees/)

Nav2 的正式导航树是可见的工程例子：按频率重算路径，失败时走上下文恢复；收到新目标时能抢占恢复；恢复成功后回主导航重新尝试。[Nav2 详解](https://docs.nav2.org/jazzy/getting_started/nav2_behavior_trees/detailed_behavior_tree_walkthrough/detailed_behavior_tree_walkthrough/) 这说明“执行器根据新事实继续”可以是确定的运行时职责，而无需每个低层动作都回到规划器。

可借用的是小型骨架：`Sequence`（有序段）、`Condition`（当前事实判断）、`Fallback`（已声明替代）、有界 `Retry/Loop`、`Subflow`（复用子策略）。不应把 BT 的 `SUCCESS/FAILURE/RUNNING` 粗暴等同于 UniClaw 的未知、Effect 在途、独立验证和权限结果；这些语义需要保留。

### 4. PDDL / PlanSys2：事实、目标、动作模型和执行者分责

PlanSys2 的架构把四件事分开：Domain Expert 保存 PDDL 类型/谓词/动作，Problem Expert 保存当前实例、事实和目标，Planner 从两者产生动作序列，Executor 激活动作执行者并在运行时检查要求。[官方设计文档](https://plansys2.github.io/design/index.html) PDDL 动作可明确给出开始/持续/结束前提和效果；其教程以 `robot_at`、电量和连通性为例，先设目标、求 Plan，再执行。[官方教程](https://plansys2.github.io/tutorials/docs/terminal_usage.html)

PlanSys2 还展示了一个常见重规划形状：外层 mission controller 更新知识或目标，重新计算 Plan，再启动新的执行。[官方 controller 教程](https://plansys2.github.io/tutorials/docs/controller_example.html) 它特别适合“领域状态足够结构化、动作效果可信”的问题。动态 Android UI 的视觉语义和安全判定不能被假装成天然完备的 PDDL 谓词；在这里它提供的是职责分离和重规划边界，不是可直接替换的技术栈。

## 应落到什么运行模型

不是“所有任务一棵树”，而是每个任务由模型从受控积木里选择适合的形状。例如：

```
目标：遍历当前可见设置入口并形成记录
策略：观察入口 → 对每个满足许可且未处理的候选：进入 → 观察该页 →
      若是可记录的值/开关则标记；若发现新的导航候选则加入待处理；返回 →
      若事实不足、页面类型未知、权限/效果未确认或预算到边界则交回模型
```

这里“对每个候选”只是一个可复用积木；另一个任务可以选择“先查条件，满足则执行 A，否则执行 B”，或“动作失败则按声明的恢复路径重试一次”。运行时只负责用最新事实推进已声明语义，不能擅自把“非白名单”解释为可操作，也不能把“点过”当作目标达成。

需要明确的回模型边界是：没有已声明的动作/条件可套用、观察与策略前提矛盾且已声明的恢复无法处理、仍需新语义判断，或到达要求复核的资源/目标/权限边界。状态未知时可先按已声明路径补证；Effect 在途未对账时由 Runtime 等待和对账，不能因咨询或换分支重复派发。逐动作观察、Guard、Assurance 和独立结果验证仍然存在；减少的是不必要的“让模型重复选择同一种下一步”。

## 不能从这些来源推出的结论

- 不能推出 Android Settings 的完整遍历可以只靠一条固定规则完成，或空候选集就是全局完成。
- 不能推出模型可安全地自行给未知 UI 分类、开放任意点击，或用自评取代独立验证。
- 不能推出一次模型调用一定更快或更便宜；策略解释、观察、条件检查和重规划都有成本，必须在同一设备/模型/权限条件下实测。
- 不能因为 BT/PDDL 成熟就直接引入完整框架。它们首先说明应补齐的语义维度：受限组合、当前事实判断、恢复、明确退出和重规划，而不是要求复制实现。
