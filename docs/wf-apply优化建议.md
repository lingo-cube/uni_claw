wf-apply 优化建议 这个工作流设计得挺有想法，把多模型协同、持续学习、质量门禁整合在一起，已经具备生产级自驱动开发的雏形。下面我从架构、实现细节、成本效率和可维护性几个角度来评价，并指出具体的优化空间。

---

## 整体评价

**优点**
- **分阶段质量门禁**：实现 → 自我验证 → 对抗验证 → 最终裁决，多轮检查能有效拦截低质量实现。
- **智能路由 + 记忆**：用历史成功率动态选择模型，避免对所有任务无脑用贵模型。
- **顺序执行避免 503**：把容易并发的验证/对抗改为顺序，实用主义的选择。
- **自动问题记录**：生成 ISSUES 文档，把未解决的风险结构化留存，方便后续跟进。
- **与原系统兼容**：复用 opsx:apply 的触发方式和设计文档读取，降低迁移成本。

**核心缺陷**
- **任务实现完全是“黑盒”**：无论是 Haiku 还是 Opus 实现，只给了一段 prompt，让模型自己“读取设计文档、理解需求、实现代码”。这极度依赖模型的自主能力，很容易发生幻觉、遗漏或理解偏差，且没有任何硬约束（比如必须运行测试、必须通过 lint）。
- **验证环节缺乏客观度量**：SelfVerify 和 Battle 还是依赖模型“觉得”好不好，没有接入实际测试执行、类型检查、lint 等确定性信号。
- **路由记忆无衰减/遗忘**：一旦某类任务 Haiku 连续失败，永久切换到 Opus，可能导致成本螺旋上升，且不会因为任务简化而回退。
- **重试机制脆弱**：任务失败后只是 `continue` 到下一轮，没有对实现进行修正再验证，可能导致同一个任务循环失败。
- **缺少对任务间依赖的动态评估**：依赖只在 `assignTask` 时简单检查，但任务完成后的连锁影响（比如实现 A 后导致任务 B 的新增依赖）完全没有处理。

---

## 详细优化建议

### 1. 给任务实现增加硬约束

现在 `haikuImplement` / `opusImplement` 只是让模型“实现代码”，然后返回一个 JSON。应该强制加入：

- **读取现有规范/设计文档**（已有提及，但没保证执行）
- **运行现有测试**，确保不破坏已有功能
- **运行 lint/类型检查**，作为 PASS/FAIL 的门禁
- **对于新功能，要求生成对应的测试**，并将其纳入后续验证环节

例如，在 `Implement` 阶段可以这样：
```javascript
// 伪代码
const impl = await agent(implementPrompt, { model });
// 硬性检查
const lintResult = execSync(`npx eslint ${impl.files_modified}`).toString();
if (lintResult.includes('error')) return { passed: false, reason: 'Lint errors' };
const testResult = execSync('npx vitest run').toString();
if (testResult.includes('FAIL')) return { passed: false, reason: 'Test failures' };
```

### 2. 把“实际运行结果”融入验证分数

SelfVerify 和 Battle 目前只依赖模型推理。应该把实际测试覆盖率、测试通过率、lint 结果等作为输入，让模型在裁决时考虑这些客观指标。Opus 的裁决 prompt 可以加入：

> 实际测试结果：10/10 通过，覆盖率 85%  
> Lint 状态：0 错误  
> 请结合以上客观结果打分。

这样评分就不会太“虚”。

### 3. 路由记忆加入衰减和代价感知

当前路由是“失败两次就永久换 Opus”，可以改为：

- **短期记忆窗口**：只参考最近 N 次同类型任务的成功率
- **失败回退阈值**：如果连续失败 2 次换 Opus，但成功后成本统计如果显示任务简单（例如 Opus 平均耗时 < 5s），可以再尝试回退到 Haiku
- **引入成本预算**：例如“本月 Opus 调用预算还剩 20 次，优先用 Haiku”，在 smartRoute 里加一个参数

### 4. 失败任务需要“修复 → 重试”流程，而非简单跳过

现在的逻辑：
```javascript
if (!implResult.passed) {
  collectIssue(...);
  continue; // 直接下一轮，可能又调度同一个任务（如果依赖未变化）
}
```
如果实现失败，应该进入一个**快速修复子流程**：
- 把失败原因（validation 的输出）喂给同一个模型或更高级模型
- 尝试修复（最多 1-2 次）
- 若仍失败，则记录 issue 并标记任务为“需人工介入”，暂时移出 pending 列表，避免死循环

### 5. 依赖管理需要更新任务状态

任务完成后，不仅要从 pending 里移除，还应该检查是否有其他任务**原本被阻塞现在可执行**，但更重要的是——**实现结果可能改变其他任务的依赖**。可以在完成阶段后增加一个 `syncDependencies`，让一个 Haiku 快速检查：

- 当前实现是否产出了一些接口/组件，正好是其他任务需要的
- 有没有任务描述可以更新为“基于已完成的任务 X，现在你可以复用它的 …”

这会让整个流程更“自驱”。

### 6. 验证/对抗的模型选择可以更动态

目前是固定的 2×Haiku + 1×Sonnet 和 1×Haiku + 1×Sonnet。可以根据任务类型动态调整：
- 复杂任务（架构/重构）：验证用 Sonnet，对抗用 Sonnet + Opus
- 简单任务（文档/配置）：可以只用 1×Haiku 验证，减少开销

这样在保证质量的前提下进一步优化成本。

### 7. ISSUES 文档的生成时机和位置

现在 ISSUES 只在所有任务循环结束后生成一次。如果长时间运行（大量任务），中间失败的信息只存在内存里，进程崩溃就丢了。建议：

- 每完成一个任务时（或至少每收集到新 issue 时）**增量写入** ISSUES 文件
- 文件路径可以基于 change 名固定，不断追加，避免丢失中间状态

### 8. 提供更清晰的人类可读进度

目前只有 console.log，但在长时间运行中，如果开发者切去干别的，回来很难快速掌握状态。可以输出一个简单的 `progress.json`，包含：

- 当前循环次数
- 已完成 / 剩余任务列表
- 最近一次错误摘要
- 累计费用估算（如果 API 返回了 token 用量）

这比纯日志更友好。

---

## 总结

这个工作流的骨架相当扎实：任务获取 → 智能分发 → 多模型验证 → 裁决 → 记录问题。最核心的优化方向是**把“模型认为好”转变为“事实层面好”**，通过接入实际测试、lint、类型检查等硬信号，大幅降低幻觉风险。另外，失败恢复、成本意识、增量持久化也是从“能用”走向“可靠生产级”的关键一步。

如果以上优化点都能落地，这套 Self-Driven Workflow 就能真正成为一个让开发者放心的“自动撸码 + 自动把关”系统。
