## 0. 一句话结论

自改进不是「让模型更聪明」，而是**让每一次失败把可执行路径的搜索空间剪掉一块，
并把剪掉的那块变成下一次启动时就已加载的资产**。

ONES 案例的形态很清楚：第一条工时是「边试边猜」（改时间这件事一开始完全不知道
怎么做），第五天的那条则是「按固定序列执行，一次通过」。加速不是推理变快了，
是**需要现场判断的分支从 N 条降到 0 条**。

推论：既然加速来自外部状态（资产、校验点、批处理策略）而非模型能力，
自改进就只能是**产品机制**，不能靠在 prompt 里多写一句「请更仔细」。

## 1. 样本还原：7 个失败—纠正对

同一个目标（给张帆登记工时）下，实际发生的认知修正。这张表是本文全部结论的
证据基础；表中的「判别依据」一列尤其重要——它决定了纠正是**猜对的**还是
**判出来的**。

| # | 现象 | 判别依据（怎么知道错了） | 纠正 | 沉淀成了什么 |
|---|---|---|---|---|
| 1 | 浏览器窗口全白，看不到任何内容 | `PrintWindow` 采样 20.8k 点，99% 是 `#F7F7F7`；改用 `CopyFromScreen` 抓真实屏幕区域结果相同；同时 `snapshot` 能读到完整 DOM → 判定为「合成层不绘制」，不是崩溃、不是没加载 | 另起一个由 Chromium 自己创建的可见窗口；或干脆只用 DOM 操作 | 环境坑：CLI 建的任务空间窗口被当作隐藏窗口，`ShowWindow` 救不回来 |
| 2 | 想找独立工时入口，跑去了效能管理 / 主页，把当前上下文弄丢 | 用户直接指出「你怎么退出去了？」；页面标题已是别处 | 回到原工作项，改为「工作项详情 → 工时页签」这一条入口 | 入口路径固化（导航不是可回退的零成本动作） |
| 3 | URL 里 4 个 `J6ZJ-xxxxx` 被当成 4 条待填任务 | 打开后读标题与页头「负责人」，发现分属王超、钱冲、张帆 | 下划线分隔的 key 是**从根到叶的层级路径**，最后一个才是当前工作项 | 「认人」硬门：负责人 ≠ 目标人就不填 |
| 4 | `fill()` 直接报 `element is read only` | 报错文本 | 开始时间是只读日期选择器，必须走选择器：打开面板 → 选小时 → 选分钟 → 点日期格 | 控件语义表（控件类型决定动作原语，不由模型临场推理） |
| 5 | 面板里已显示新时间，失焦后回滚成原值 `15:00` | 提交后**回读** `input.value`，发现不是期望值 | 点完日期格必须再按 `Enter` 才算提交 | 假成功防线（本文第 5 节） |
| 6 | 小时列里的 `09` 点不到 | 单元格 `y` 为负，点击落在面板矩形外，面板被关掉 | 先 `col.scrollTop = cell.offsetTop - col.clientHeight/2`，再取 `getBoundingClientRect()`，并校验点是否落在面板矩形内 | 几何前置校验（点击前先证明「它此刻真的可见可点」） |
| 7 | 点击被浮层拦截 / 「盲点空白坐标」把详情弹窗关掉 | 报 `intercepts pointer events`；页面回到了列表页 | 不用盲坐标，一律取 `rect` 中心再点；`Escape` 或清掉 `.ones-popover-mask` | 坐标纪律（盲点 = 不可判定动作） |

其中 #5 和 #1 是两类完全不同的坑：#1 是一次性环境问题，#5 是会**反复骗人**的
语义问题。二者的处理优先级应当不同——这正是第 3 节「排序」要解决的。

## 2. 为什么后面变快了：三种收缩

「一开始不知道怎么改时间，后面越改越快」不是熟练度，是三次可命名的收缩。

### 2.1 路径收缩：从「搜索」变成「执行」

改时间的可行路径从「试 fill / 试点输入框 / 试点日历 / 试敲键盘」收敛为唯一序列：

```
点开始时间 → 等面板出现 → 选小时(滚动到可见) → 选分钟 → 点日期格 → Enter → 回读校验
```

判据很硬：这条序列**不再包含需要现场判断的分支**。一旦某条路径里还有
「看情况」，就说明还没收缩完。

### 2.2 判定收缩：从「看起来对了」到「可判定」

同一件事的成功定义经历了三次收紧：

1. 面板里显示新值（错：会回滚）
2. `input.value === "2026-10-19 09:00"`（对，但只管这一层）
3. 三层交叉：成员明细逐条 `登记 10月19日 09:00 开始，实际投入 8 小时` → 汇总
   `总已登记工时 40 小时` → 动态累计 `8 / 16 / 24 / 32 / 40`

第 3 层才是「任务完成」的判据。**成功定义收紧一次，可被伪造的空间就少一层。**

### 2.3 范围收缩：从「全量试错」到「样本 + 批量」

实际节奏是先试填 1 条（10/19，8h）把整条链路跑通，再按同一序列批量补齐其余 4 天，
且**每轮校验、任一轮失败立即停**。这条策略同时买到两个东西：验证成本被压到 1 条，
错误暴露面被压在最小批次内。

> 三条收缩的共同点：都不改变模型，只改变**系统带着什么状态开始下一次执行**。
> 这就是「自改进」在工程上唯一可实施的位置。

## 3. 自改进闭环：六步，每步都有产物和判据

```
Capture ──► Classify ──► Rank ──► Promote ──► Verify ──► Regress
 捕获纠正对   归到失败类   按阻断排序   晋升为资产   同任务复跑   改版即失效
```

| 步骤 | 做什么 | ONES 实例 | 产物 | 判据（做到什么算这一步完成） |
|---|---|---|---|---|
| **Capture 捕获** | 记录四元组：症状 / 判别依据 / 纠正动作 / 校验点 | 第 1 节的 7 行 | 一条可复现的纠正记录 | 换个人按记录能复现同一症状并判定 |
| **Classify 归类** | 归入失败分类学（见下） | #1→环境渲染，#4→控件语义，#5→假成功 | 带分类键的记录 | 同一类记录能在**别的应用**上被映射 |
| **Rank 排序** | 按「阻断率 × 修复成本」排，而不是按发现顺序 | #5（纯假成功、每次都骗）优先于 #1（一次性环境坑） | 待晋升队列 | 排序能被解释，且不依赖主观感觉 |
| **Promote 晋升** | 固化为**可执行资产**，不是写进 prompt 的文本 | #4/#5/#6 → 固定选择器序列；#3 → 前置门 | 脚本 / 能力原语 / preflight 检查 | 资产执行时不需要模型再做判断 |
| **Verify 验证** | 用同一批任务复跑，看曲线 | 40 小时 10 条记录一次补齐 | 前后对比数据 | t_n 下降、假成功率下降、断点数不上升 |
| **Regress 回归** | 站点改版时让**资产先崩**，而不是任务静默填错 | 未发生，见第 8 节 P2 | 可回放场景 | 失败信息是「资产过期」而非「任务失败」 |

### 失败分类学（从本案例归纳，7 类）

| 类 | 症状特征 | 本案例 | 迁移性 |
|---|---|---|---|
| 环境渲染 | 窗口/画面空白但 DOM 正常 | #1 | 低（一次性） |
| 入口导航 | 找错入口、丢上下文 | #2 | 中（同产品内高） |
| 身份与范围 | 认错人、把层级当列表 | #3 | 高（跨产品） |
| 控件语义 | `read only`、必须走选择器 | #4 | 高（同类组件库） |
| 几何可见 | 元素在视口外/被滚动容器裁掉 | #6 | 高（跨产品） |
| 时序遮挡 | 浮层拦截、提交后未刷新 | #7 | 高（跨产品） |
| 假成功 | UI 短暂呈现目标态后回滚，或根本没写库 | #5 | 高（**最贵**） |

分类的价值不在归档，在于**迁移**：#4、#5、#6 大概率会在下一个基于同类组件库的
站点上重现；#1 则是一次性成本，不值得做通用机制。把这两类混在一起排序，
资源就会被一次性坑占满。

## 4. 四类可复用资产

自改进的产出必须落成这四类之一，否则只是「这次运气好」。

| 资产 | ONES 实例 | 在 UI 自动化里的形态 | 失效信号 |
|---|---|---|---|
| **操作原语** | 只读日期 = 打开→时→分→日→Enter→回读 | 确定性子过程（Effect Provider 内），不交给模型每次推理 | 站点换组件库，面板结构变化 |
| **失败模式库** | 第 1 节 7 条坑位表 | 按「站点/控件类型/症状」检索的记忆条目，**命中才注入**，不常驻上下文 | 命中率下降（症状出现但没被召回） |
| **校验链** | 明细 → 总量 → 动态累计 | Expected Effect 的具体对照物（写清「凭什么算完成」） | 验证通过但下游仍报错 |
| **场景回放** | 「填 5 天 = 40 小时」 | 可重放 case，用于改版回归 | 场景长期不跑，过期不自知 |

关键约束：**原语能下沉就下沉**。凡是「每次都要模型想一遍才能点」的动作，都是
尚未固化的资产；凡是固化了的，就应当移出模型判断路径，交给确定性执行器。

## 5. 第一风险是「假成功」，不是「失败」

失败会停下，假成功会继续走，并让错误在下游放大。ONES 案例里最贵的一步
（#5）就是：面板短暂显示了新时间，值却在失焦后回滚成默认 `15:00`；如果不回读，
后续 9 条都会以错误时间提交，而报告会显示「已填写 40 小时」。

三条防线，按成本从低到高：

1. **回读权威值**：读 `input.value` / 服务端汇总，不读操作后的瞬时 UI 状态；
2. **失焦后再读一次**：专门针对选择器、下拉、级联这类失焦即回滚的控件；
3. **多源交叉**：明细条目 + 汇总总量 + 动态/审计流水三者一致才算完成。

这与 `CONTEXT.md` 已有的分离是同一条：**Effect Receipt（投递留痕）≠ Verified
Effect（动作后的观察确认）**。工时案例是这条分离在真实外部系统上的一次实证：
点击「确定」成功（有留痕）不等于工时写进去了（需回读确认）。

度量上必须单列：`假成功率` 应与 `成功率` 分开统计，否则「看起来完成」会把
曲线抹平。

## 6. 前置门：速度只在正确方向上才有价值

案例里存在一个「又快又错」的险些发生：URL 里有 4 个 key，若按「4 条任务批量填」
推进，会把工时填到王超、钱冲名下——执行得越顺，破坏越大。

因此三类判定必须在动作之前、且不可被「效率」绕过：

| 门 | 判据 | 失败时的正确行为 |
|---|---|---|
| **身份门** | 弹窗「成员」/ 工作项「负责人」== 目标人 | 停下，换工作项，不硬填 |
| **范围门** | URL 层级路径 ≠ 任务清单；确认当前对象是叶节点 | 重新解析，不按直觉批量 |
| **不可逆门** | 提交即写库；回滚只能靠删除记录 | 先规划后执行，**不在不可逆动作上试错** |

推论：试错只允许发生在**可观察、可回滚**的环节（打开面板、点格子、清浮层）。
这也是「第一次只填 1 条」这条策略的本质——把试错关进最小可回滚范围。

## 7. 怎么证明「真的变快了」

自改进最容易自欺的地方，是把「这次没报错」当成「改进了」。建议固定看这几条曲线：

| 指标 | 定义 | ONES 基线观察 |
|---|---|---|
| 首次通过率 | 不改任何东西一次跑通的比例 | 首条工时：0（需 4~5 轮试探）；第 2~5 条：接近 1 |
| 单条耗时衰减 `t1/tn` | 同型任务第 n 次的耗时 / 第 1 次 | 从「每步都要试」到「按序列连填」 |
| 断点数 | 需要人类介入的次数（登录 handoff 计 1） | 登录 1 次；其余全程无人工干预 |
| 假成功率 | 报告成功但回读/交叉验证不成立的比例 | #5 前后从「会中招」降到 0 |
| 新坑发现率 | 每次执行新增的失败类条目数 | 收敛到 0 = 资产对本站点已饱和 |
| 迁移成本 | 换一个同类站点需新增多少次试错 | 尚未测量（P2） |

判据：一次「改进」算数，需要 **t_n 下降 ∧ 假成功率不上升 ∧ 断点数不上升**，
三条同时成立。只看其中一条必然被骗——例如把批量跑得飞快但漏校验，
t_n 会显著下降而假成功率飙升。

## 8. 落地路线

### P0（不改架构，靠 skill + 脚本即可）

1. **任务结束强制产出纠正清单**：四元组不写出来，任务不算完成；
2. **任务开始先加载坑位表**：按站点/控件类型检索，命中才注入；
3. **提交前后各一次回读**：动作前读旧值、动作后读新值并断言；
4. **样本先行**：任何批量操作，先跑 1 条并验证全链，再放开。

### P1（进入产品机制）

1. 失败分类作为**检索键**（站点 × 控件类型 × 症状），而不是全文搜索；
2. 稳定原语下沉为确定性执行器（Effect Provider 内的子过程），移出模型判断路径；
3. 把「提交 5 天 = 40 小时」这类任务固化为可回放场景，纳入回归；
4. 错误发生后走 Recovery（重新观察 → 重新定位），而不是重跑整个任务——
   案例中「盲点坐标关掉弹窗」应当是一次局部恢复，不该导致从头来。

### P2（跨应用）

1. **迁移矩阵**：失败类 × 应用，显式标注「已知不可迁移」（如 #1）；
2. **资产过期检测**：站点改版后，先崩的应该是资产，报「资产失效」而非
   「任务失败」——这是自改进系统与普通脚本的根本区别；
3. **迁移成本度量**：新站点达到「一次通过」所需的试错次数，作为资产质量指标。

### 与现有词汇的落点（候选，非权威）

| 本文概念 | 现有落点 | 说明 |
|---|---|---|
| 失败模式库 | Strategy Memory（`ui-automation-knowledge-and-memory-design.md`） | 本文补的是**记录格式与晋升判据**，不新建存储层 |
| 操作原语 | Effect Provider / DeliveryTarget | 控件语义决定动作序列，属于执行侧确定性能力 |
| 校验链 | Expected Effect / Verified Effect | 「凭什么算完成」必须是可判定的对照物 |
| 局部恢复 | Recovery / Traversal | 失败后重定位，不重跑 |
| 场景回放 | scenarios / 回归资产 | 让资产过期可见 |

## 9. 反模式

1. **把试错写进常驻 prompt**：上下文通胀，且旧步骤会被照抄执行；
2. **用模型自述「已完成」当证据**：#5 的「面板显示新值」就是自述，必须回读；
3. **让资产免检**：记住了 ≠ 还对，站点改版后旧序列会静默出错；
4. **只记成功路径，不记失败判别**：加速来自「判别依据」，不是来自「最终脚本」；
5. **用单次任务总时长当改进指标**：会被一次性环境坑污染（本案 #1 占掉大量时间），
   应看 `t1/tn` 衰减与假成功率；
6. **在不可逆动作上试错**：工时/订单/删除类操作，先规划后执行。
