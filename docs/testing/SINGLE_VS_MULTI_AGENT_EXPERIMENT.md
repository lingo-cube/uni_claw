# 单Agent vs 多Agent对比实验

> **Experiment**: Single Agent vs Multi-Agent Comparison
> **目标**: 验证多Agent架构在分析质量和效率上的优势

---

## 实验设计

### 目标模块

**state_machine** - 状态机模块

选择理由：
- 复杂度中等（有Global FSM、Traversal FSM、Node Stack三层）
- 有完整的设计文档
- 有明确的测试场景需求
- 之前分析过，有基准参考

### 对比维度

| 维度 | 单Agent | 多Agent | 衡量方式 |
|------|---------|---------|----------|
| **完整性** | 1个Agent找所有 | 多个Agent并行找 + Battle验证 | 找到的方法/场景数量 |
| **准确性** | 可能遗漏 | Battle互相找遗漏 | Battle发现的问题数量 |
| **效率** | 串行执行 | 并行执行 | 执行时间 |
| **成本** | 全部Opus | Haiku为主 | 模型使用统计 |
| **质量** | 单一视角 | 多视角 + 对抗验证 | 场景覆盖深度 |

## 实验流程

### 单Agent流程

```
┌─────────────────────────────────────┐
│         Single Opus Agent           │
│                                     │
│  1. 代码分析 ────────────┐          │
│  2. 文档分析 ────────────┤          │
│  3. 场景提取 ────────────┼─→ 综合   │
│  4. 边界识别 ────────────┤          │
│  5. 错误识别 ────────────┘          │
│                                     │
│  6. 记录遇到的困难                 │
│  7. 记录潜在的遗漏                 │
└─────────────────────────────────────┘
        ↓
   分析结果 + 自我评估
```

**特点**：
- ✅ 一致性强（单一视角）
- ❌ 容易遗漏（没有验证）
- ❌ 串行执行（慢）
- ❌ 全部Opus（贵）

### 多Agent流程

```
Phase 1: 并行分析 (Haiku)
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ Agent 1      │  │ Agent 2      │  │ Agent 3      │
│ 代码分析     │  │ 文档分析     │  │ 测试分析     │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                  │                  │
       └──────────────────┴──────────────────┘
                          │
Phase 2: Battle验证
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ Agent 4      │  │ Agent 5      │  │ Agent 6      │
│ 验证代码分析 │  │ 验证文档分析 │  │ 一致性检查   │
│ (Haiku)      │  │ (Haiku)      │  │ (Sonnet)     │
└──────────────┘  └──────────────┘  └──────┬───────┘
                                            │
Phase 3: 场景提取
┌──────────────────────────────────────────┐
│ Agent 7: 快速生成 (Haiku)               │
└──────────────┬─────────────────────────┘
               │
┌──────────────▼─────────────────────────┐
│ Agent 8: 优化补充 (Opus)               │
└──────────────┬─────────────────────────┘
               │
Phase 4: 综合评估
┌──────────────▼─────────────────────────┐
│ Agent 9: 综合评估 (Opus)               │
│  - 整合所有分析结果                    │
│  - 评估Battle发现                     │
│  - 给出质量评分                        │
└───────────────────────────────────────┘
```

**特点**：
- ✅ 并行执行（快）
- ✅ Battle验证（更全面）
- ✅ 分层模型（便宜）
- ✅ 多视角（更准确）

## 预期结果

### 完整性对比

| 指标 | 单Agent预期 | 多Agent预期 | 改进 |
|------|-------------|-------------|------|
| 发现的方法数 | 8-10 | 12-15 | +50% |
| 发现的依赖数 | 5-7 | 10-13 | +80% |
| 提取的场景数 | 15-20 | 25-35 | +75% |

**理由**：
- 单Agent可能因为上下文限制遗漏内容
- 多个Agent并行分析，覆盖更全面
- Battle互相找遗漏

### 准确性对比

| 指标 | 单Agent预期 | 多Agent预期 | 改进 |
|------|-------------|-------------|------|
| 错误识别 | 基本正确 | 经过Battle验证 | 更准确 |
| 边界识别 | 可能有遗漏 | Battle互相补充 | 更完整 |
| 一致性检查 | 无 | 专门的Agent检查 | 新增能力 |

**理由**：
- Battle Agents专门找问题
- 一致性Agent检查代码vs文档
- 多视角发现单一视角看不到的问题

### 效率对比

| 指标 | 单Agent | 多Agent | 说明 |
|------|---------|---------|------|
| 代码分析 | 30s | 30s | 同样时间 |
| 文档分析 | 20s | 20s | 同样时间 |
| 场景提取 | 40s | 10s+30s | Haiku快+Opus慢 |
| 总耗时 | 90s | 60s | 并行节省时间 |

**理由**：
- 多Agent并行执行代码和文档分析
- Haiku快速生成基础场景
- 只有关键步骤用Opus

### 成本对比

| 模型 | 单Agent | 多Agent | 节省 |
|------|---------|---------|------|
| Opus调用 | 1 | 2 | -50% |
| Sonnet调用 | 0 | 1 | N/A |
| Haiku调用 | 0 | 6 | 新增但便宜 |
| **Token成本** | 100% | 30% | **-70%** |

**理由**：
- 单Agent全部用Opus（最贵）
- 多Agent大部分用Haiku（最便宜）
- Haiku成本低廉

## 关键发现预期

### 发现1: 遗漏的内容

**单Agent**：
- 可能遗漏不常用的方法
- 可能遗漏深层的边界条件
- 可能遗漏代码vs文档的不一致

**多Agent**：
- Battle Agents专门找遗漏
- 预计发现 5-10 个额外的问题

### 发现2: 场景覆盖深度

**单Agent**：
- 场景覆盖基本路径
- 可能遗漏边界组合
- 可能遗漏错误场景

**多Agent**：
- 场景覆盖更全面
- Battle确保边界和错误都有覆盖
- 预计多 30-50% 场景

### 发现3: 一致性问题

**单Agent**：
- 无法发现代码vs文档的不一致
- 无验证机制

**多Agent**：
- 专门的Agent检查一致性
- 预计发现 2-5 个不一致

### 发现4: 执行效率

**单Agent**：
- 串行执行，总时间 = 各项时间之和

**多Agent**：
- 并行执行，总时间 = max(各项时间)
- 预计快 1.5-2x

## 实验价值

### 验证多Agent的优势

通过实验验证：
1. **完整性**: 多Agent是否真的找到更多内容
2. **准确性**: Battle是否真的发现问题
3. **效率**: 并行是否真的更快
4. **成本**: 分层是否真的更便宜

### 优化架构

基于实验结果：
1. 调整Agent配置
2. 优化模型选择
3. 改进Battle机制
4. 平衡质量和成本
