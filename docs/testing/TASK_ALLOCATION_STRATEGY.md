# 任务分配策略 - Opus架构师决策体系

> **版本**: V1.0 | **日期**: 2026-06-08
> **核心**: Opus架构师根据任务属性智能分配验证资源

---

## 任务分类体系

### 按任务类型分类

| 任务类型 | 描述 | 验证重点 |
|----------|------|----------|
| **新功能 (new_feature)** | 实现新的功能模块 | 完整性、覆盖率 |
| **Bug修复 (bug_fix)** | 修复现有bug | 回归测试、修复验证 |
| **重构 (refactor)** | 代码重构不改变功能 | 兼容性、迁移性 |
| **测试 (testing)** | 添加或改进测试 | 测试质量、覆盖率 |

### 按复杂度分类

| 复杂度 | 判断标准 | 资源分配 |
|--------|----------|----------|
| **LOW** | 单一函数、独立模块、无复杂依赖 | Haiku × 1-2, NORMAL Battle, 1次迭代 |
| **MEDIUM** | 多个函数、模块间交互、有依赖 | Haiku × 3, INTENSIVE Battle, 2次迭代 |
| **HIGH** | 跨模块、复杂状态、高风险依赖 | Haiku × 3, Sonnet × 2, INTENSIVE Battle, 3次迭代 |

### 按风险等级分类

| 风险 | 判断标准 | 应对策略 |
|------|----------|----------|
| **LOW** | 不影响核心功能、易于回滚 | 标准验证流程 |
| **MEDIUM** | 影响部分功能、需要数据迁移 | 加强验证、增加回归测试 |
| **HIGH** | 影响核心功能、难以回滚、高风险依赖 | 最严格验证、多轮Battle、人工审查 |

## 资源分配规则

### Agent分配

| 验证阶段 | Agent | 模型选择 | 触发条件 |
|----------|-------|----------|----------|
| 需求分析 | Haiku | Haiku | 所有任务 |
| 代码分析 | Haiku | Haiku | 所有任务 |
| 数据准备 | Haiku | Haiku | 所有任务 |
| Battle验证 | Sonnet | Sonnet | 复杂度>MEDIUM 或 风险>MEDIUM |
| 场景提取 | Haiku | Haiku | 所有任务 |
| 代码生成 | Haiku | Haiku | 所有任务 |

### 迭代策略

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **aggressive** | 快速迭代，1-2次即可 | LOW复杂度、LOW风险 |
| **balanced** | 平衡迭代，2-3次 | MEDIUM复杂度、MEDIUM风险 |
| **conservative** | 保守迭代，3+次 | HIGH复杂度、HIGH风险 |

## 质量门禁

### 通过标准

| 维度 | 门禁值 | 说明 |
|------|--------|------|
| **完整性** | ≥90% | 所有必需场景都已覆盖 |
| **准确性** | ≥85% | 分析结果准确无误 |
| **一致性** | ≥90% | 各Agent结果一致 |
| **质量** | ≥85% | 代码质量达标 |
| **综合评分** | ≥85/100 | 整体质量合格 |

### 强制通过条件

即使评分略低，以下情况也可以通过：
1. 所有关键需求都有测试覆盖
2. 没有严重的遗漏或错误
3. 代码可以运行并产生预期结果
4. 已达到最大迭代次数

### 拒绝条件

以下情况必须拒绝：
1. 关键需求缺少测试
2. 存在严重的逻辑错误
3. 测试无法运行
4. 与需求严重不符

### 技能增强

修改 `.claude/skills/openspec-apply-change/SKILL.md`，在Step 6后添加：

```markdown
**6.5. 测试验证闭环** (可选)

在标记任务完成前，可以选择执行测试验证闭环：

```bash
/Workflow multi-agent-test-validation-tiered --task {task_id}
```

这将：
1. Opus架构师理解任务需求
2. 制定测试验证策略
3. 分配Agent执行分析
4. 生成高质量测试代码
5. 验证测试质量
6. 生成验证报告

**检查清单**：
- [ ] 测试通过 (`pytest tests/`)
- [ ] 覆盖率达标 (≥85%)
- [ ] 验证报告合格
```

### 自动化集成 (可选)

在 `openspec/hooks/` 创建 `test_validation_hook.py`:

```python
#!/usr/bin/env python3
"""测试验证Hook - 集成到/opsx:apply流程"""

def validate_task_tests(task_id, change_name):
    """验证任务的测试是否通过"""
    import subprocess
    import json

    # 1. 生成测试
    result = subprocess.run([
        'claude', 'code', 'workflow',
        'multi-agent-test-validation-tiered',
        '--task', task_id
    ], capture_output=True, text=True)

    if result.returncode != 0:
        return {'status': 'failed', 'reason': '测试生成失败'}

    # 2. 运行测试
    result = subprocess.run([
        'pytest', 'tests/', '-v', '--tb=short'
    ], capture_output=True, text=True)

    if result.returncode != 0:
        return {'status': 'failed', 'reason': '测试未通过'}

    # 3. 检查覆盖率
    result = subprocess.run([
        'pytest', 'tests/', '--cov=src/', '--cov-report=json'
    ], capture_output=True, text=True)

    with open('coverage.json') as f:
        coverage = json.load(f)

    if coverage['percent_covered'] < 85:
        return {'status': 'failed', 'reason': f'覆盖率不足: {coverage["percent_covered"]}%'}

    return {'status': 'passed', 'coverage': coverage['percent_covered']}
```

## 总结

**核心改变**：
1. Opus作为整体把控者，理解任务→制定策略→分配任务→验证结果→决策
2. 根据任务类型、复杂度、风险动态分配资源
3. 持续验证循环，直到质量达标或达到最大迭代次数
4. 与/opsx:apply自然集成，形成完整闭环

**效果**：
- 更智能的资源分配
- 更高的测试质量
- 更完整的验证闭环
