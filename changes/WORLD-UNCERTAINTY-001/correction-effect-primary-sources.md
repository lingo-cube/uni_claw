# 错误语义影响与补偿：一手资料及迁移边界

日期：2026-10-23。Authority NONE。性质：设计参考，不引入新Owner或通用Saga机制。

## 官方资料原意

- [Microsoft Azure Architecture Center：Compensating Transaction pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) 讨论跨步骤、最终一致操作部分成功后的恢复：记录已完成步骤及相应补偿信息；补偿用于处理已完成工作的影响。
- Azure指出不能简单把系统恢复到操作开始时的状态，因为并发工作可能已改变中间状态；补偿通常是应用特定的业务逻辑，并不保证回到原始状态，也未必严格按原步骤反序执行。
- 补偿动作可能失败，重试时应具备幂等性，并应能关联、审计原操作与补偿过程；需要保存足够信息以恢复处理。某些步骤不可逆，须标明不可返回点；有些失败只能人工介入。
- 这些规则针对分布式业务操作的失败恢复。本文只引用其“按已发生影响做有依据的补偿”原则，不把页面认识纠错等同于一笔业务Saga。

## 对本设计的有限迁移

- 若第一版页面语义有误，后续纠正须先由原动作/消费Owner判断当前状态、影响范围、可补偿性、明确补偿目标及执行权限；World对错误认识的修正本身不等于已逆转外部效果。
- 尚未执行的提案可由原Owner按当前依据阻止或撤销；执行中由原Owner按其生命周期停止、完成或恢复；已执行的效果须按当前状态与业务规则判断是否补偿、采用何种目标，或转人工处理。不能一概“最后完整回滚”。
- 对已派生Slice或已关联结果的错误语义，应沿来源与实际依赖重判受影响的当前表达/后续判断；不得只修最新显示，也不得让同一错误来源支撑的后续检查自证正确。
- 纠正只产生新的World认识与必要的新投影。历史Slice和已发生的Outcome保留原事实及来源；不得把历史Outcome改写成未发生，也不得把补偿伪装成原操作从未发生。

## 不能由资料推出

- 不推出自动执行补偿、统一补偿流程、所有场景必须整批修复或回到第一版之前的状态；补偿目标、权限与可逆性须由原Owner依当前状态和业务规则裁决。
- 不要求新增通用Saga引擎、让模型投票，或全仓重做；不可逆、歧义或无法安全补偿时，应保留真实结果并交由既有Owner/人工处理路径。

## 设计反例

1. 初始语义错误，后续检查只沿同一错误依据复用，结果“通过”：不能把自洽当成独立确认；应暴露共同来源并重判受影响判断。
2. 错误语义已派生Slice、驱动动作并产生Outcome：纠正World投影不能抹掉动作事实；须由原Owner核实实际效果及是否需要补偿。
3. 同一误判分别处于未执行、执行中、已执行阶段：分别由原Owner判断撤销提案、处理中止/恢复、已完成效果的补偿或人工处置，不能套用一个回滚动作。
4. 补偿后再查看历史Outcome：保留原操作和补偿各自发生的记录；当前解释反映补偿后的状态，不回写历史为“从未发生”。
