     先例），交叉对表后统一修订。

   **Grill 方法要求（owner 2026-10-16 补充）**：
   ① **对照业界通行做法**——每条被攻击的机制，除内部自洽性外，须对照
   业界 harness 的实际做法（设计稿 §3 对照表为起点，grill 中可扩充：
   Claude Code / Codex / ACP / MCP 等）作参照论证：我们与通行做法的
   差异是"维度化编排"的有意取舍，还是无据的偏离——两类结论的处置
   不同（前者补叙事，后者改设计）。
   ② **约束变更用场景直白话**——凡 grill 中确认需要改变的既有约束，
   结论必须以直白、带具体场景的表述陈述（例：「弹窗只有 button1 可见
   时，现词表会点到确定键，真的会改系统设置——所以词表必须改」），
   不得停留在抽象原则层（例：「词表安全性不足」）。每条约束变更 =
   场景 + 后果 + 改法三件套，让不做架构的读者也能复核。
