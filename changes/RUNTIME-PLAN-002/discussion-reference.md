## 2. 前面已经讨论清楚的方向

- 菜单项可以看作子树入口；进入菜单后动态发现子节点，处理完返回。模型不必预先列出所有菜单或每一步点击。
- 对菜单遍历，范围、起点/结束位置、节点规则、安全约束、深度和结束条件是主要任务描述。展开、去重、维护父路径、返回及继续处理应由稳定算法承担。
- 计划树表达任务意图，UI节点/页面关系表达已知环境。两者都可以呈树形，但不是同一对象；现实导航有共享子页和回路，因此需要图关系与判重。
- 与Behavior Tree的共同点是树形组织行为；差异主要在节点语义和推进方式。无需先决定采用通用BT，也无需让模型为每个菜单拼Sequence/Selector/Repeat。
- 其他交互可以复用或组合策略；地图等需要专门能力的交互必须有具体观察、动作、反馈和结束判据。提供一个扩展接口不能算已经适配。
- 安全策略属于全程执行约束。菜单或按钮外观不代表安全，黑名单未命中不代表允许。计划只能收紧任务授权，不能扩权。
- 新页面仍符合已有规则时继续；需要新语义判断、规则不适用、安全/事实未知或需要资源复核时反馈给模型。每步观察、安全检查和验证保留。

## 3. 输入、执行、输出对照稿

下表用于敲定语义，不是字段表。树和图是数据结构；“执行”指执行器怎样消费它们，不能给数据结构赋予独立权威。

| 对象 | 输入 | 执行时如何使用 | 输出及消费者 |
|---|---|---|---|
| 计划树 PlanTree | 任务目标、范围、当前事实摘要、已提供能力、授权与安全限制 | Agent形成/修订任务规则；Runtime校验采纳，按声明策略展开；Traversal选择下一处理项，经既有Control/Assurance/Effect/验证链推进 | 版本化计划供Runtime消费；执行产生的节点结果、未完成项、停止原因与修订需求，由Runtime记录并反馈给Agent |
| 遍历图 Traversal Graph（D1-D3已确定） | 按任务范围从World有依据结构中摘取引用，覆盖累计已观察页面/元素/关系；不输入任务处理标记 | 组织成可重建的结构视图供Traversal消费；结合独立任务进度选择进入/返回方向；World更新后反映当前有效性 | 已知页面、元素及关系的引用视图，供Traversal推进、计划适用性检查和Agent复核；历史定位不直接作为当前动作目标，不输出任务进度结论 |

计划树的输出不只是展示文本；遍历图的输出不提供点击许可。上表中的结果是对应Owner的产物，并非树或图自行宣布的事实。

Owner在第1轮选择A，替代原先“图包含任务标记”的候选稿：遍历图只描述已知环境结构；任务进度单独记录已处理、待处理、受阻等。Traversal结合两者；反馈给模型时可以组合展示。结构事实与处理标记各自保持World/Run来源，组合展示不等于新增事实源或扩大图的定义。

第2轮选择A：累计保留任务范围内已观察、有依据的结构，不把历史引用变成当前可点击目标。第3轮澄清B为从World摘取任务所需结构引用、组织成可重建视图，Owner随后指示“下一步”，据此按B继续：World是唯一世界事实源，遍历图不独立创造或反写事实；查询或缓存的物理方式后定。

D4已按Owner“按推荐”确定：调用方提交计划树并关联任务，由Runtime经显式World/Run等Owner读取缝，按需取得派生遍历图、Run进度与当前约束；遍历图不是上层必须另行提供的参数。原四类只是执行依赖的信息分类，不冻结字段，不引入隐藏全局依赖或新增事实源。

D5按Owner要求改为：调用方发起一次Traversal执行，运行中通过只读查询了解状态，本次执行结束后才取得结果。原“每推进一项向调用方返回”的草案不作为对外接口；内部处理与查询不代替Kernel完整执行链或产生新的Run真值。查询本身不触发执行、隐式续行或模型咨询。

D6按Owner选择A确定：受阻需新决策时暂停原执行，保留位置、进度、已做工作及预算账本；Kernel通过既有咨询取得明确决定，在合法边界重检事实/授权后继续或修订。暂停不立刻返回最终结果，取消/超时/预算/停止仍按既有规则处理，在途Effect先对账。

D7/D8已按Owner“按推荐”确定：查询只读提供状态/执行位置/进度/暂停原因及待决定事项的概览，明细按引用取得；最终执行报告交代结束方式与原因、完成/未完成工作、跳过/未知及证据引用。不冻结字段/状态枚举，不将Traversal结果直接作为Goal完成证明。

## 4. 两者如何形成闭环

```text
目标、范围、能力和安全约束 → Agent生成计划树
调用方提交计划树并关联任务 → 发起一次Traversal执行
Kernel执行驱动在原Run内协调 → 按需读取World/Run等Owner
World的结构事实 → 派生遍历图；当前Run的处理结果 → 独立任务进度
执行期间：计划树＋遍历图＋任务进度 → 内部持续选择下一处理项
下一处理项 → 既有安全执行链 → 新观察和独立验证
新观察事实 → World更新 → 刷新图；执行结果 → 更新Run任务进度
调用方可只读查询状态；本次执行结束后返回结果
受阻需新决策 → 暂停原执行 → Kernel取得明确决定 → 合法边界重检后继续/修订
```

需要保持三项区别：意图与事实分开；世界事实与任务进度分开；算法结束与任务完成分开。图本身不携带“待处理项”；Traversal结合图和任务进度判断是否还有工作，任务完成仍需原目标证明。

## 5. 用一个菜单例子对照

用户要求：只读检查设置，安全菜单进入、控件记录、危险项不点，限定最大深度，处理完回到首页。

```text
计划树：Traverse设置
├─ 范围：设置首页下的授权范围
├─ 处理规则：安全菜单展开；控件记录；禁止项标记；未知按约定留缺口或暂停
├─ 安全约束：只读授权，逐操作检查
└─ 限制与结束：最大深度、Run预算、返回首页、覆盖及缺口可核对
```

假设某轮已经观察并验证“设置→网络→Internet”，图提供这段已知关系，独立任务进度记录这次任务已经处理了哪些项。模型无需事先写出Internet。执行器完成这段子树后返回父位置，继续处理已发现的其他入口；若返回后无法确认位置，反馈受阻，不猜测下一次点击。

控件状态来自观察，处理标记来自执行结果；未进入的危险子树只能标注未探索。只读任务的完成条件必须允许并披露这些排除，否则不能把“全部可安全处理项已处理”写成“所有页面已检查”。

## 6. 已收敛的三条边界与最终复核

1. **输入边界（D1-D4已定方向）**：调用方提交计划并关联任务，运行时按需读取World派生结构引用、Run进度与有效约束；具体粒度按场景收敛，未知与当前有效性不得隐去。
2. **执行边界（D5/D6已定方向）**：对外一次持续执行，内部走Kernel完整链；受阻需决策时暂停同一次执行，明确决定与重检后继续/修订。
3. **输出边界（D7/D8已定方向）**：运行中查询只读概览，明细按引用；本次执行结束返回含结束原因、成果/缺口及证据引用的报告，任务完成仍由原证明链判断。

这三条边界与菜单例子已集中到flow-contract.md，等待最终共同理解确认；其他场景作为后续适配检验。此阶段不冻结节点目录或字段级协议，不宣布场景适配完备。
