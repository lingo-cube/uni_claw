# PlanTree / Traversal / handlers的数学推导

日期：2026-10-19。基于D1-D16；本文件给出定义、条件命题、证明纲要和反例，**不是机器验证的产品正确性证明**。

后续D17-D19澄清见[第12轮](grill-round-12.md)：领域完成/通过/有效性判据由各handler能力协议提供，Kernel不重判；不符合按声明策略记录或暂停，具体恢复归Recovery。本文关于判据/恢复的条件义务按此归属解释。原有限图/三值规则模型不含这些领域策略，仍只是D1-D16历史参考检查。

## 1. 先定义“完备”

不能以“树能嵌套”或“状态机能运行”推导全UI完备。至少区分：

| 层 | 命题 | 本次结论 |
|---|---|---|
| 输入追溯 | 固定清单每个ID均有归属 | 可由审计程序检查 |
| 相对表达 | 给定已声明能力与判据，固定任务类可构造计划 | 对有限结构任务有条件构造；尚未覆盖所有任务类 |
| 分支处置 | 正常/未知/失败/取消/超时/能力缺失都有合法出口 | D1-D16给出主要语义，K3-K6仍有细节义务；合法拒绝不等于完成任务 |
| 安全性 | 任意执行前缀不发生所定义的违规转移 | 依赖原Owner缝正确且新编排不绕过；只能给归纳证明义务 |
| 活性 | 某个合规待处理项最终被处理，或执行最终退出 | 需公平调度、响应/超时、有限工作等假设 |
| 覆盖 | 明确定义的有限可达目标均处理 | 依赖发现、身份、深度、返回及充足预算 |
| 实现与现实 | 实际程序精化上述模型，观察/动作吻合现实 | 本次未证明，不能由纸面推导或小模型检查取得 |

安全与活性应分开证明；这是并发程序正确性中的基本区分，原始论述见[Lamport 1977](https://lamport.azurewebsites.net/pubs/proving.pdf)。以下具体模型及反例是本次针对UniClaw的推导。

## 2. 数学对象

令真实环境状态为x，观察为o=Obs(x)，World根据接纳证据产生W_t。W_t不是x本身。任务相关遍历视图为G_t=Project(W_t,scope)，其中节点、关系及依据引用均来自World；关系失效可使G_t缩减，不假定图只增不减。

计划P包含范围S、限制D/B、有序规则R和结束义务O。规则r_i=(m_i,a_i)，其中m_i只用已声明判据求值；a_i为具体交互或只读处理，具有自己的H_before和H_after。每个handler是任务绑定能力的typed操作引用及参数/输入关联/继续条件，不是任意可执行代码。

一个分析用执行配置可写为：

```text
z = (P版本, W引用, G视图引用, Run进度J, 当前位置/待处理项F,
     当前操作a及attempt, handler位置k, 阶段q, 剩余预算b, 有效授权引用)
```

这不是要求新增一个聚合Owner或wire对象；各分量仍由原Owner保存，执行器经显式缝协调。J中的处理记录不是World事实，handler Finding也不是Goal或安全裁决。

## 3. 有序规则的确定性命题

把已知匹配结果归一为T/F/U；Unsupported、冲突或缺证若不能求值则作为U处理，不删除原诊断原因。

一个可确定选择i的充分条件是：

```text
m_i = T，且对所有j<i，m_j = F。
```

若最早的非F为U，则不能越过它选择后项；若全F则是无规则匹配，不能隐含生成默认点击。对固定规则序和固定判据结果，可选择结果至多一个：若i<k都满足，上式要求m_i同时为T和F，矛盾。

更强的解释：任一U都有多种可能补证结果。只有在所有与当前信息相容的补全中选择不变，才能称选择有依据。参考检查枚举三条规则的27种三值输入，并用全部布尔补全检查每次确定选择；同时保留“把U当F”误选的最小见证。该检查不能证明判据本身正确或字段足够。

首项匹配的确定性不推出规则正确性：把“普通控件”放在“危险按钮”前面仍可能选错；独立安全gate不能被该选择豁免。规则遮蔽和任务语义覆盖需单独审查。

## 4. 分阶段执行与安全归纳

分析用阶段为：选定→前置handler→执行/等待对账→独立验证→后置handler→记录处理结果。只读操作没有Effect投递，但仍有输入有效性和完成判据。失败、取消和未知不是成功后置阶段的同义词；现有post-commit事件也不等于某操作验证完成。

要保持的归纳不变量：

1. **权限不增**：一次计划/handler可用权限是Run授权与当前产品策略的交集，不能由页面文字/规则/Finding增加。
2. **当前依据**：实际交互必须经当前接地、绑定、Assurance与Effect边界；前置检查通过不免除投递时复核。
3. **串行屏障**：前一有Effect操作未对账和验证，不能以运行后置handler或推进下一交互冒充成功。
4. **账本单调**：计划修订/暂停不删除已消耗预算、失败或已投递事实；已发生动作不会因后置检查失败而“撤销发生”。
5. **来源保持**：遍历视图和结果不改写World身份/依据；完成报告不自行满足原Goal。

证明纲要：初态由合法Run采纳建立上述约束；匹配/只读查询不投递，保持权限；前置handler的所有有Effect行为若存在也必须走同一gate；投递转移仅在完整原链成立时发生；新证据分别更新原Owner；验证后再推进；暂停/修订保留账本且恢复前重检。逐转移保持才能推出任意有限前缀保持。

这是**条件归纳**：原链可靠、新增typed适配遵守边界、时序原子性/失效检查正确，是待验证前提。真实环境可能在检查后突变；若物理系统不提供足够强的时序/动作语义保证，最多保证“基于当时有效依据获准投递”，不能保证现实永远无危险。不能从tap获准推出tap的现实效果一定只导航。

## 5. 有限菜单覆盖定理

固定本次任务所需的抽象状态域Q；状态须足以区分会改变处理义务的页面、相关内容、任务阶段、允许范围及必要返回上下文，不能仅用UI树形状或屏幕hash。令E为受支持且授权允许探索的关系。深度上限D以计划根为0；为了讨论不同到达深度，将状态提升为(q,remainingDepth)。

假设：

- A1：相关状态域在此任务中有限且稳定，或变化可使相应完成记录失效并最终稳定。
- A2：同一相关状态可被正确判同；不同任务义务不因同页而被合并。
- A3：每个应展开状态的全部合规入口最终能被枚举，有可判定的局部结束依据。
- A4：操作、后验和handler最终给出结果或可控超时；合法返回/重定位可用。
- A5：规则为每个必需节点选得所需操作，所需能力可用，必需继续条件最终可满足。
- A6：调度公平；处理某一路径不会永久饿死另一已知必需项。
- A7：预算足以覆盖所定义目标；深度截断、禁入和未知被目标范围明确接纳或列作缺口。

结论：采用保留待处理入口、按相关义务判重且不丢弃较浅到达展开机会的遍历，将处理所有深度≤D内的必需可达处理项，并在规定返回位置可验证时正常结束。

证明：根为基例。对可达路径长度d归纳；若d<D的前驱已展开，由A3其入口进入待处理集合，A2保证不被错误合并；由A4-A6最终得到进入/已处理的有依据结果。对同状态更充足的剩余深度保留展开机会，故不会漏掉其允许的新后继。归纳覆盖至D。由有限状态与有限深度，提升图有限；在不无意义重复处理、每项工作最终返回的实现条件下，待办最终耗尽。A7允许完成而不是被预算提前截断。

若任务要求的是“测试每条导航边”或“每个入口的文字”，则覆盖单位必须是边/入口处理义务，不能只标记目标页visited。页面覆盖、入口覆盖、控件检查覆盖是不同集合。

### 5.1 全局visited的反例

```text
root→A→C→D
root→C
最大深度=2，先走A分支。
```

C先在深度2被标visited；随后root→C在深度1再次到达。若全局visited直接跳过C，则漏掉本应可达的深度2节点D。修正义务是保留更好深度/不同相关上下文的展开机会，具体键与算法后定。参考模型用该4节点图复现错误，并验证提升状态的参考遍历与最短路径可达集一致。

### 5.2 复杂度的正确口径

对固定、已完整给出的提升图及常数成本访问，图遍历可按其状态/边数计成本；实际UI还要加发现、返回、检查、等待和模型成本。任务相关上下文可能使状态数大于页面数。不能宣称总耗时只取决于页面数，也不能由本证明推出咨询次数或延迟收益。

## 6. 预算、等待和终止

有限预算只限制被计费的工作。若handler永久卡住、等待没有可调度的超时，预算不变，执行仍可永久停留。深度限制也不限制同页无限滚动。

条件命题：若每个非等待推进消耗至少一个有限工作额度，所有外部调用均可在有限时间返回或交还控制，超时/取消在公平调度下必可生效，且跨修订不自动补预算，则执行在有限工作后正常结束、暂停或受控停止；若还要求暂停最终结束，必须额外保证独立总时限/停止事件可达。D1-D16已有受限等待方向，但精确计费/取消/超时执法属于K6。

所以“不会无限动作”“一定结束”“一定完成目标”是三个不同命题。耗尽预算只证明当前执行须退出/等待裁决，不能证明覆盖充分。

## 7. 组合与恢复

若每个子处理满足前置/后置契约，父处理只有在子结果满足要求时推进，且外部干扰保持所依赖的前提，才可用结构归纳组合。共享World、预算、授权、窗口及在途动作使子任务相互影响；单独测试各handler不能推出组合正确。

最小反例（仅限明确必需的继续条件）：点击已验证成功→后置检查不满足而暂停→从整个act开头恢复→再次点击（可能返回上页/重复提交）。仅记录的不符合不会触发这条恢复路径。Kernel须提供operation attempt、handler位置与结果等事实；Recovery据此处理具体恢复，handler能力判断自身输入/结果有效性。“同一Traversal暂停”不等于“该act可从头重放”，也不要求Traversal实现Recovery策略。

另一个反例：前置检查授权有效→用户撤销→投递。若只用前置结果就投递，违规；原gate必须按有效授权再检查。在途撤销也不能追溯取消已经发生的Effect。账本去重最多阻止重复投递请求，不能无条件保证外部系统恰好发生一次效果。

## 8. 全UI无条件完备性的两个反证

### 8.1 观察不可区分

构造两个环境e0/e1：在任意有限观察前缀里显示相同列表；e0到此结束，e1在更深处还有必需条目。没有可信末端信号时，任何只依赖该前缀的执行器都作相同选择。若宣称全覆盖，则在e1错误；若一直继续，则不能保证在e0有限结束。随机化也不能提供对所有环境零错误的有限结束保证。

因此不能同时无条件承诺：对任意开放UI、有限终止、绝不遗漏、且不需要发现前提。暂停/保留缺口正是诚实的语义出口，不是成功适配证明。

### 8.2 任意可计算目标

若允许UI背后运行任意程序M，并在M停机时出现“完成”目标；一个能对所有此类任务有限判定是否终将完成的通用算法将决定一般停机问题。该承诺不能成立。计算能力的通用性不提供全知判定，参见[Turing原论文](https://www.cs.virginia.edu/~robins/Turing_Paper_1936.pdf)。

这里的结论只针对无界任意程序/目标；**不否定有限明确模型的遍历与模型检查**。D1-D16目前没有定义通用机器指令、无界存储或通用计算的编码/模拟证明，不能仅凭树、循环或引用Capability就称PlanTree图灵完备；即便底层宿主可运行通用计算，也不等于受限计划语言或有限授权Run具备同一承诺。
