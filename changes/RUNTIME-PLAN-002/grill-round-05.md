# Grill 第5轮：一次推进向Runtime返回什么

日期：2026-10-19。状态：Owner调整Q5，确立D5为“提供状态查询，执行完才返回结果”；原逐次推进返回提案不采用为对外接口。

## 前提

调用方提交计划树并关联任务；Runtime经既有Owner读取缝按需取得世界结构派生图、Run进度与当前约束。Traversal不拥有Effect投递、安全许可或任务完成权威。正常规则可以持续机械展开，不逐处理项咨询模型。

## 当前前沿 Q5

是否将Traversal一次推进的结果分为四类？

| 结果 | 表示什么 | 后续职责 |
|---|---|---|
| 可推进 | 找到下一项语义处理请求，例如进入菜单、记录控件、返回或补充观察 | Runtime经原Control/安全执行链处理；有现实动作则必须取得新观察并独立验证后推进 |
| 等待 | 已发起动作或观察，但结果尚未明确 | Runtime等待或按既有有界对账机制处理；不盲重发、不仅因等待就重新咨询模型 |
| 受阻需决策 | 当前计划规则无法覆盖，已有范围内补证/恢复仍不能解决，或需既有预算复核 | 返回原因与事实给既有咨询/停止路径，不扩权、不凭Traversal宣称失败或完成 |
| 当前计划段结束 | 该策略/节点的工作已达到声明的局部结束条件 | Runtime记录结果，按父计划继续或交原任务证明链；不单独判定Goal完成 |

推荐采用四种语义，避免把“需要继续观察”“已有动作在途”“需要改计划”和“局部做完”混为一谈。结果不包含执行许可、过期坐标或直接投递权；实际请求的接地/授权/投递仍由原Owner完成。

记录控件或选择下一项也消耗既定本地工作量；局部机械推进不获得新预算。终局、取消、安全拒绝和资源到顶继续沿用既有Run/Contract规则，不在Traversal结果旁另造终态权威。

## 后续

Q5答复后确定验证结果怎样反馈进度、何时继续/修订及局部结束怎样交任务证明链；随后用一个动态菜单例子复核完整流程。无需先冻结实现接口。

## 答复

Owner先问Runtime是否就是Kernel，已澄清本文Runtime指Kernel内部负责Run推进的执行驱动/协调职责，当前主要对应KernelRunDriver，不是新运行组件。

Owner随后明确“Traversal应该提供状态查询，执行完才返回结果”。记录D5：对外是一次持续执行，运行中只读查询状态，本次执行结束才交付结果；不要求调用方反复取下一处理项来驱动循环。原表描述的逐项推进/等待/受阻不能作为对外每步返回协议；可在内部或状态视图中区分，但具体状态/终局结果目录尚未由Owner确认。

这不改变内部Kernel唯一Run推进、Control意图、安全许可、Effect投递及独立验证链。Traversal的查询从同源Run/执行记录派生，只读且不触发动作、隐式续行或咨询；不是新状态Owner，也不是第二个Run驱动。Traversal执行结束不自动证明Goal完成。

当前尚待定的是“受阻需模型决策”应暂停原执行等待修订，还是结束本次执行并返回受阻结果，转第6轮，不实施产品。
