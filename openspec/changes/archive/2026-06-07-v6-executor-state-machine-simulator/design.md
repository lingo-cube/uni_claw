## Context

### 当前状态

Uni-Claw V5.x 系列已实现 AI 集成和视觉管道优化，但核心遍历控制逻辑存在以下问题：

1. **状态机不完整** - 缺少关键状态（容器帧完成、异常处理、弹窗处理）
2. **执行逻辑分散** - 遍历引擎、状态机、异常处理耦合在 `traversal_engine.py` 中
3. **测试依赖真实设备** - 无法离线验证遍历逻辑，开发迭代慢
4. **计划模型缺失** - 无法声明式定义遍历策略（完成条件、深度限制等）
5. **可视化不足** - 遍历过程难以理解和调试

### 约束条件

1. **向后兼容** - 不破坏现有 API 和行为
2. **模块化** - 新组件应可独立测试
3. **可扩展性** - 支持未来添加新的退出策略、完成策略
4. **性能** - Trace 记录不应显著影响执行速度

### 利益相关者

- 开发者：需要清晰的架构和可测试的组件
- 测试工程师：需要离线测试能力
- 运维人员：需要详细的 Trace 用于问题诊断

## Goals / Non-Goals

**Goals:**

1. **完整的声明式遍历计划** - 支持通过 JSON 定义完整遍历策略
2. **清晰的状态机** - 所有执行状态和转换路径明确，无隐藏逻辑
3. **可测试的执行引擎** - 支持使用 Mock 组件离线测试
4. **详细的执行追踪** - 记录每个状态转换，支持多种可视化格式
5. **三层兜底异常处理** - 节点策略 → 异常链 → AI，确保鲁棒性

**Non-Goals:**

1. 不改变现有的视觉管道（保持 V5.x 的 AI 集成）
2. 不修改全局状态机（GlobalFSM）
3. 不实现新的 AI 策略（仅预留接口）
4. 不改变 ADB 接口（复用现有 ActionExecutor）

## Decisions

### D1: 数据类层次结构

**决策**：使用 Python `@dataclass` 定义所有新模型，采用组合而非继承。

**理由**：
- 数据类提供默认 `__init__`、`__eq__`、`__repr__`
- JSON 序列化/反序列化更容易
- 组合提供更灵活的模型演化

**替代方案**：使用 Pydantic 模型
- 优点：内置验证、更好的类型提示
- 缺点：引入新依赖，与现有代码风格不一致

### D2: 状态机实现方式

**决策**：扩展现有 `TraversalStateMachine` 类，添加新状态和处理方法。

**理由**：
- 保持与现有代码的一致性
- 最小化变更范围
- 状态转移逻辑集中管理

**替代方案**：创建全新的状态机类
- 优点：不影响现有代码
- 缺点：代码重复，维护成本高

### D3: 仿真模拟器架构

**决策**：SimulationRunner 包装 GraphTraversalEngine，注入 Mock 组件。

**理由**：
- 执行引擎逻辑保持一致
- Mock 组件可独立测试
- 易于验证真实设备与仿真的一致性

**替代方案**：创建独立的仿真引擎
- 优点：完全隔离
- 缺点：实现复杂度高，可能出现行为差异

### D4: Trace 格式

**决策**：使用内存中 TraceStep 列表，支持多种导出格式（JSONL、HTML）。

**理由**：
- 内存格式高效，支持实时查看
- 多种导出格式满足不同需求（JSONL 用于机器处理，HTML 用于人工查看）
- 易于扩展新的可视化格式

**替代方案**：直接写入文件
- 优点：简单
- 缺点：不灵活，无法支持多种格式

### D5: 异常处理顺序

**决策**：三层兜底 - 节点 error_policy → ExceptionHandlingChain → AI。

**理由**：
- 局部优先（节点策略）→ 全局兜底（异常链）→ 智能恢复（AI）
- 每一层可以独立配置和测试
- AI 作为最后的兜底，可以处理未预见的情况

## Risks / Trade-offs

### 风险 1: 状态机复杂度增加

**风险**：新增三个状态可能导致状态转换逻辑难以理解和维护。

**缓解措施**：
- 在代码中添加详细的状态转移图注释
- 编写完整的单元测试覆盖所有转换路径
- 使用 Mermaid 图表可视化状态机

### 风险 2: 仿真与真实设备行为不一致

**风险**：Mock 组件可能无法完全模拟真实设备行为，导致测试通过但实际失败。

**缓解措施**：
- Mock 组件接口与真实组件保持一致
- 定期使用真实设备验证仿真结果
- 在 CI 中保留少量真实设备测试

### 风险 3: Trace 开销影响性能

**风险**：详细的状态转换记录可能影响执行速度。

**缓解措施**：
- Trace 记录可通过配置禁用
- 使用高效的数据结构（列表而非频繁的字典操作）
- 仅在需要时序列化到文件

### 权衡 1: 灵活性 vs 复杂性

**权衡**：支持多种退出策略和完成策略增加了配置灵活性，但也增加了复杂性。

**选择**：提供合理的默认值，大部分场景无需自定义配置。

### 权衡 2: 特性完整 vs 快速交付

**权衡**：一次性实现所有特性 vs 分阶段交付。

**选择**：按 PRD 定义的阶段实施，确保每个阶段可独立验证。

## Migration Plan

### 阶段 1: 图模型补全（1-2 天）

1. 在 `src/graph/node.py` 添加新枚举和数据类
2. 创建 `src/graph/plan.py` 实现 TraversalPlan
3. 编写单元测试

### 阶段 2: 状态机扩展（2-3 天）

1. 扩展 `TraversalStateMachine` 添加新状态
2. 实现状态处理方法
3. 更新状态转移逻辑
4. 编写单元测试

### 阶段 3: 执行器实现（3-4 天）

1. 创建 `src/traversal/graph_engine.py`
2. 实现初始化流程和主循环
3. 集成 Trace 记录
4. 编写单元测试

### 阶段 4: 仿真模拟器（3-4 天）

1. 创建 `src/simulation/` 目录和模块
2. 实现 Mock 组件
3. 实现 SimulationRunner
4. 实现可视化输出
5. 编写端到端测试

### 阶段 5: 集成与验证（2-3 天）

1. 集成到现有代码
2. 回归测试
3. 性能验证
4. 文档更新

### 回滚策略

所有新增代码放在新文件中，现有代码仅做最小扩展。如果出现问题，可以：
1. 禁用图模式，继续使用传统遍历
2. 删除 `src/simulation/` 目录不影响主流程
3. 恢复 `src/graph/node.py` 和 `src/state_machine/traversal_fsm.py` 的修改

## Open Questions

   - **决议**：暂不实现，预留接口。V6.1 再集成。

2. **模板注册表格式**：TemplateRegistry 的 JSON 格式是否需要标准化？
   - **决议**：复用现有格式，不做修改。

3. **Trace 持久化**：是否需要支持实时写入文件？
   - **决议**：V6 仅支持内存累积后导出，实时写入留待 V6.1。

4. **并发执行**：是否需要支持多个遍历并行？
   - **决议**：V6 不支持，预留扩展接口。
