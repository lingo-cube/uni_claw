# Uni-claw 架构设计文档

## Context

Uni-claw 是一个 AI 驱动的移动端 UI 自动遍历框架，通过 AI 视觉分析和 ADB 控制自动探索移动 APP 的完整界面结构。

### 当前状态

V1 版本已实现核心遍历功能，包括：
- 多 Vision Provider 支持（Claude、MiMo）
- ADB 设备控制抽象
- 状态管理和持久化
- 遍历引擎核心逻辑
- 基础异常处理

### 技术栈

- **语言**: Python 3.x
- **AI 模型**: Claude 3.5 Sonnet, MiMo v2.5
- **设备控制**: ADB (Android Debug Bridge)
- **依赖管理**: UV, Pydantic

### 设计原则

1. **接口优先**: 核心组件基于抽象接口，易测试和扩展
2. **状态分离**: 状态管理独立于业务逻辑
3. **程序管状态，AI 管识别**: 路径决策由程序负责，AI 只负责识别
4. **非侵入式**: 仅通过截图 + 点击交互

## Decisions

### 1. 三层架构设计

**决策**: 采用 TraversalEngine + ADBClient + VisionService 三层架构

**理由**:
- **关注点分离**: 引擎负责逻辑编排，ADB 负责设备控制，Vision 负责 AI 分析
- **可测试性**: 每层可独立 Mock，便于单元测试
- **可扩展性**: 新增 Vision Provider 或 ADB 实现无需修改核心逻辑

**替代方案**:
- 单体类：拒绝，缺乏灵活性，难以测试
- 两层架构（合并 ADB 和 Vision）：拒绝，二者职责差异大

### 2. 接口抽象模式

**决策**: 所有核心组件使用抽象接口（ABC）

```python
class ADBClient(ABC): ...
class VisionService(ABC): ...
```

**理由**:
- **依赖注入**: 便于注入 Mock 实现
- **多实现支持**: Claude、MiMo、Mock 可共存
- **契约保证**: 编译期检查接口完整性

### 3. 状态持久化策略

**决策**: 使用 JSON 文件存储状态，支持断点续跑

**理由**:
- **简单性**: 无需额外依赖（数据库）
- **可读性**: JSON 可人工检查和调试
- **轻量级**: 适合单机遍历场景

**数据结构**:
```python
TraversalState:
  - current_path: list[str]      # 当前路径
  - visited: set[str]             # 已访问元素
  - all_level1_menus: dict        # 一级菜单缓存
  - level2_menus_cache: dict      # 二级标签缓存
  - items_cache: dict             # 内容元素缓存
  - content_tree: ContentTree     # 层级结构树
```

### 4. 坐标缓存策略

**决策**: AI 识别一次后缓存坐标，后续复用

**理由**:
- **节省成本**: 减少 AI 调用次数
- **提高速度**: 避免重复识别
- **稳定性**: 坐标比视觉识别更可靠

**缓存键设计**: `"level1|level2"` 作为 items_cache 的 key

### 5. 异常处理枚举化

**决策**: 使用 ClickResult 枚举定义所有可能的点击结果

**理由**:
- **类型安全**: 编译期检查所有情况
- **完整性**: 强制处理所有分支
- **可扩展**: 新增场景只需添加枚举值

```python
class ClickResult(str, Enum):
    NO_CHANGE = "no_change"
    POPUP = "popup"
    PAGE_JUMP = "page_jump"
    NORMAL = "normal"
    NO_FEEDBACK = "no_feedback"
    ERROR = "error"
```

### 6. Pydantic 数据模型

**决策**: 使用 Pydantic BaseModel 定义所有数据结构

**理由**:
- **类型检查**: 自动类型验证
- **序列化**: 内置 JSON 序列化/反序列化
- **文档性**: 类型即文档

### 7. 事件系统设计

**决策**: 使用回调函数方式提供实时事件通知

**理由**:
- **解耦**: 引擎不依赖具体的日志/监控实现
- **灵活性**: 用户可自定义事件处理
- **轻量级**: 无需引入消息队列等复杂依赖

```python
def on_event(event: TraversalEvent):
    print(f"[{event.event_type}] {event.data}")

engine = TraversalEngine(..., event_callback=on_event)
```

## 组件职责表

| 组件 | 职责 | 不负责 |
|------|------|--------|
| TraversalEngine | 遍历逻辑编排、异常处理 | 具体 AI 调用、设备操作 |
| ADBClient | 截图、点击、返回键等设备操作 | 业务逻辑 |
| VisionService | AI 视觉分析、入口定位 | 遍历决策 |
| StateManager | 状态持久化、数据缓存 | 业务逻辑 |
| ContentTree | 层级结构存储和导出 | 状态转换 |

## Risks / Trade-offs

### 已知限制

| 限制 | 影响 | 缓解方案 |
|------|------|----------|
| 无状态机 | 异常恢复依赖手动逻辑 | 后续实现 HierarchicalStateMachine |
| 无图像指纹 | 无法验证点击有效性 | 后续集成指纹验证 |
| 无按钮类型区分 | 所有元素统一处理 | 后续添加 expected_action 字段 |
| 单线程执行 | 遍历速度受限 | 当前为功能验证阶段，可接受 |

### 设计权衡

1. **Pydantic vs 数据类**
   - 选择 Pydantic：更强验证、更好序列化
   - 代价：额外依赖、轻微性能开销

2. **JSON 数据库 vs 真数据库**
   - 选择 JSON：简单、无依赖、可读性强
   - 代价：并发支持弱、大规模数据性能差
   - 判断：当前单机场景足够

3. **回调事件 vs 发布订阅**
   - 选择回调：简单、无依赖
   - 代价：不支持多监听器
   - 判断：当前单消费者场景足够
