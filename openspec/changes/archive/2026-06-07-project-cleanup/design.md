# Design: Project Cleanup

## Context

### Current State

uni-claw 项目当前存在以下组织问题：

1. **根目录临时文件混乱**: 15个临时 Python 脚本和 9个 Markdown 文档散落在根目录，缺乏组织
2. **测试结构不清**: 单元测试和集成测试混合在 `tests/` 目录，未按功能分离
3. **缺乏清理规范**: 没有明确的临时文件管理规范，导致文件不断积累
4. **Git 状态混乱**: 288个 `.traces/*.jsonl` 文件已删除但未提交

### Constraints

- **零功能变更**: 本次清理仅涉及文件移动和重组，不改变任何业务逻辑
- **测试兼容性**: 所有测试必须在重组后继续正常运行
- **低风险执行**: 采用"先移动，后删除"策略，确保文件不会意外丢失
- **时间限制**: 整个清理过程应在 45 分钟内完成

### Stakeholders

- 开发团队：需要清晰的代码组织和维护规范
- CI/CD 系统：测试路径配置可能需要更新
- 新开发者：需要清晰的入职文档和项目结构

---

## Goals / Non-Goals

**Goals:**

1. 建立清晰的项目目录结构，根目录仅保留必要文件
2. 将单元测试移至 `src/` 模块目录，集成测试保留在 `tests/`
3. 创建长期维护规范，防止未来继续积累无用文件
4. 清理 Git 状态，提交已删除的文件
5. 更新配置文件以支持新的结构

**Non-Goals:**

- 不改变任何业务逻辑或功能实现
- 不重构测试代码（仅移动文件位置）
- 不修改 CI/CD 配置（仅测试路径可能需要更新）
- 不建立自动化清理工具（手动流程即可）

---

## Decisions

### 1. 清理策略：安全归档优先

**决策**: 采用"先移动到归档，后审查删除"的策略，而非直接删除。

**理由**:
- 降低误删风险：文件移动后可随时恢复
- 给审查时间：可以在不紧急的情况下仔细评估每个文件
- 渐进式清理：可以分批次处理，不会一次性改动太多

**替代方案考虑**:
- **直接删除**: 风险太高，可能丢失有用文件
- **询问后再处理**: 耗时太长，难以执行

### 2. 测试重组：单元测试与源码同目录

**决策**: 单元测试放在 `src/模块/` 目录，与被测试代码同目录。

**理由**:
- 就近原则：测试代码与实现代码距离近，便于维护
- 清晰分离：单元测试（单组件）vs 集成测试（多组件）界限明确
- 符合惯例：许多 Python 项目采用这种组织方式（如 Django）

**替代方案考虑**:
- **所有测试放在 tests/**: 单元和集成测试混在一起，难以区分
- **tests/unit 和 tests/integration**: 增加导入复杂度，测试与代码距离远

### 3. 脚本组织：按功能分类子目录

**决策**: `scripts/` 目录下按功能创建子目录（analysis, debug, verify, visualization, tmp）。

**理由**:
- 功能明确：按用途组织，易于查找
- 便于清理：tmp/ 目录可以定期清理
- 清晰结构：开发者知道新脚本应该放哪里

**替代方案考虑**:
- **所有脚本平铺在 scripts/**: 文件多时难以管理
- **按模块组织（scripts/ai/, scripts/traversal/）**: 跨模块脚本难以归类

### 4. 文档整合：保留有用信息，删除临时报告

**决策**: 临时测试报告直接删除，有用信息整合到 `docs/`。

**理由**:
- 测试报告过时快：旧测试报告对当前开发无参考价值
- 避免重复：根目录文档应与 docs/ 下的文档整合
- 保持整洁：避免根目录文档膨胀

### 5. Gitignore 扩展：覆盖常见临时文件模式

**决策**: 扩展 `.gitignore` 以覆盖所有常见的临时文件模式。

**理由**:
- 预防性措施：防止未来临时文件被意外提交
- 覆盖全面：包括报告、可视化、HTML 等多种临时输出
- 维护简单：模式清晰，易于理解和维护

## Risks / Trade-offs

### Risk 1: 测试路径变化导致 CI/CD 失败

**描述**: 移动测试文件后，CI/CD 系统可能找不到测试。

**缓解措施**:
- 更新 pytest 配置以支持新路径
- 在合并前验证所有测试仍然可以运行
- 提供 CI/CD 配置更新指南

### Risk 2: 移动文件导致 Git 历史混乱

**描述**: 文件移动会创建 Git rename 记录，可能影响历史追踪。

**缓解措施**:
- 使用 `git mv` 而非手动移动，保留历史记录
- 在提交信息中清楚说明文件移动
- 移动后验证 `git log --follow` 仍然有效

### Risk 3: 归档文件被遗忘，永远不清理

**描述**: 文件移到归档后，可能永远不会被审查和删除。

**缓解措施**:
- 设置 7 天审查期限
- 在归档目录创建 README 说明审查流程
- 定期提醒团队审查归档文件

### Risk 4: pytest 配置不当导致测试发现失败

**描述**: 配置错误可能导致某些测试不被发现。

**缓解措施**:
- 移动后运行 `pytest --collect-only` 验证测试发现
- 检查单元测试和集成测试都能正确发现
- 提供测试运行指南

## Migration Plan

### 阶段 1: Git 状态清理 (5 分钟)

1. 提交已删除的 288 个 trace 文件
   ```bash
   git add -A
   git commit -m "chore: remove 288 stale trace files from .traces/"
   ```

### 阶段 2: 创建安全归档 (5 分钟)

1. 创建归档目录
2. 移动根目录临时文件到归档
3. 验证根目录已清理

### 阶段 3: 恢复有用文件 (10 分钟)

1. 创建目标目录结构
2. 从归档恢复有用文件到正确位置
3. 验证恢复的文件可以正常工作

### 阶段 4: 整合文档 (15 分钟)

1. 检查需整合的文档内容
2. 提取有用信息到新文档
3. 删除临时文档

### 阶段 5: 测试重组 (10 分钟)

1. 移动单元测试到 `src/` 模块目录
2. 移动集成测试到 `tests/` 子目录
3. 更新 pytest 配置

### 阶段 6: 配置更新 (5 分钟)

1. 更新 `.gitignore`
2. 更新 `pyproject.toml` 或 `pytest.ini`
3. 验证配置正确

### 回滚策略

如果出现问题：
- 使用 `git mv --force` 将文件移回原位置
- 恢复配置文件到清理前状态
- 从归档恢复误删的文件
