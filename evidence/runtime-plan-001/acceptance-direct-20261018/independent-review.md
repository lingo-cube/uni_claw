# ADR-0053 direct-transport acceptance: independent review

## Review scope and status

Read-only review of the fixed procedure, service transport evidence, frozen-entry snapshots, current comparison metadata/guard changes, and prior implementation inventory. No model output or in-progress Step trial result was read. No test, build, device action, or model invocation was run by this reviewer. The five Step trials are still in progress; this is a pre-result review, not acceptance of the direct-transport performance outcome.

## Specification axis

**The new batch is properly separated from earlier proxy and Pro epochs.** `procedure.md` fixes the same product target, bounds, coverage, action policy, Prompt/Profile 17, and provider selection for the Flash direct run, and explicitly forbids merging prior proxy or Pro results into direct gains. Its planned baseline is three valid known-path samples and two candidate samples, followed by strict pre-Plan freeze; Plan counts are fixed at ten total and there is no “run more until PASS” path. Failed or rejected attempts remain in cost numerators, token gaps remain unknown, and no money or statistical-significance claim is planned. This is an appropriate finite acceptance batch, subject to reporting the baseline/sample limitations.

**The late-lock mechanism remains available in the shared freeze script, but the new procedure does not invoke it.** Current `freeze_thresholds.py` requires positive, explicit known/candidate sample counts and computes required valid baseline counts from those arguments. It retains the prior same-condition Plan-existence guard, so the prescribed `--name flash-direct --known-samples 3 --candidate-samples 2` call is a strict freeze. The procedure must be followed in that order: all required Step evidence and metrics first, successful freeze next, then the first Plan. If required Step samples are invalid, the fixed one-time replacement allowance applies; insufficient valid baseline means stop without manufacturing gates.

**Direct-transport identity is now part of the measurement condition.** `RuntimePlanComparisonLiveTests` requires the transport evidence path and records both path and SHA-256 in each experiment. `run_trial.py` requires this evidence, checks before the trial that the only listener on port 3081 has the recorded service PID, and re-hashes the recorded launch environment file against the captured hash. The freeze script adds `transportEvidenceSha256` to the condition key when present, so same-provider/model/artifact trials with a different proxy/transport snapshot cannot join this direct baseline. The five frozen-entry files reproduce the exact hashes in their manifest; comparing the current copies with those snapshots shows only the declared transport metadata additions in the C# test, plus the explicit sample-count and transport-identity guards in the two measurement scripts. Those deltas do not alter product behavior.

**The captured service evidence proves direct transport readiness, not yet every later model request.** `transport.json` identifies the newly started `uniclaw-product` PID 85912 on 3081, hashes the `/Users/fran/.dsh/.env` launch snapshot, records `deepSeekProxied: false`, and shows a no-key/no-model 401 probe with a direct remote socket. The socket log contains connections from that service PID to the recorded DeepSeek addresses. The no-key probe cannot by itself prove a credentialed model request used the same route. Before classifying the eventual trials as direct, compare each experiment’s PID/env/transport hashes with `transport.json` and confirm the service-PID socket monitor spans the actual model calls, not only startup probing. If service PID or environment hash changes, that trial must not silently enter this cohort.

**Reusing old functionality evidence is valid only for unchanged implementation identity.** The 74-item implementation inventory agrees with the currently hashed files except for `RuntimePlanComparisonLiveTests.cs`, whose delta is confined to transport evidence capture. The earlier functional tests and code review may therefore be carried forward for unchanged Kernel/Host/Agent/Prompt behavior, as the verification record requires; they do not establish transport routing or the performance result of this batch. The Pro and earlier Flash proxy comparison numbers remain separate and cannot satisfy any direct gate. The Host.Dsh log records the focused suite at 34/34; its NuGet vulnerability-feed warning and test nullable warning did not cause the suite to fail.

## Standards axis

The intervention follows the owner-owned configuration boundary: the owner changed `NO_PROXY`/`no_proxy`; this reviewer sees no agent-authored proxy or credential mutation. Reusing the existing 3081 product profile and reloading its owned process preserves the existing endpoint/profile boundary. The checked-in product prompt and product behavior were not changed for this transport acceptance. Only comparison evidence metadata and its strict collection/freeze guards were added. The actual provider bundle hash remains pinned. The device lease shown in `device-start.txt` is `emulator-5556`; no other device is claimed.

## Provisional conclusion

No specification or standards blocker is visible in the fixed acceptance procedure or the reviewed metadata-only delta. The batch has not yet earned a direct-transport performance conclusion: all Step trials, model-session identity/usage checks, frozen threshold record, and the ten fixed Plan trials remain to be reviewed when complete. The prior proxy and Pro measurements are context only. Keep the Change in VERIFY unless the direct batch meets all registered gates and the unchanged runtime acceptance requirements.

## Final direct batch review

### Arithmetic, registration, and accounting

The fixed ten Plan invocations are all recorded with exit 0 and valid completion; no replacement or additional Plan was started after the fixed set. `thresholds-flash-direct.json` remains the pre-Plan freeze at 14:12:20 UTC, hashes the unchanged baseline file, and records `registrationTiming: before-any-plan`, `transportEvidenceSha256: fa0e923c…`, Flash, provider artifact `3c05833a…`, and Profile/Prompt 17. `threshold-registration.txt` and `threshold-script-precheck.json` show the first registration attempt failed before any Plan because historical Flash rows lacked a provider artifact field; filtering those records with `dict.get` allowed the strict freeze to complete without changing baseline bytes or formula. The corrected freeze succeeded before ShortPlan/9, so there is no late-lock deviation.

Arithmetic in `comparison-result-flash-direct.json` matches the fixed thresholds. Known Step has 4 attempts/3 valid, averaging 3.6667 consultations, 7.3333 calls, 96,345.33 tokens and 26,597.133 ms; it is a baseline, not a Plan pass. Known ShortPlan is 3/3 at 2 consultations, 4.3333 calls, 53,831.33 tokens and 23,261.823 ms; all gates pass. Known RulePlan is 3/3 at 2.3333 consultations, 5 calls, 64,654.67 tokens and 20,858.614 ms; only the frozen ≤2 consultation gate fails. Candidates ShortPlan is 2/2 at 3 consultations, 6 calls, 98,449 tokens and 30,969.570 ms; candidates RulePlan is 2/2 at 2 consultations, 4.5 calls, 59,721.5 tokens and 29,554.651 ms; both candidate groups pass all gates. Thus 3 of 4 Plan groups pass; the direct epoch as a whole does not pass.

All 16 direct-epoch trial rows (six Step attempts including the one invalid attempt, and ten Plans) have matching Flash/provider-artifact/transport conditions; all four Plan groups have complete token and actual-call accounting. The `formal-trial-audit.json` records deepseek-official/deepseek-flash, reasoning off, matching transport hash, and `actualCallsWithPositiveReportedUsage` equal to each session's measured modelCalls. Direct batch total is 91 model calls and 1,340,375 reported tokens, with zero missing usage across its 16 sessions. The failed known Step/12 attempt contributes 4 calls and 44,447 tokens to baseline cost, while its invalid completion is excluded from the valid denominator; it is included in the known Step mean used for the token/time ceilings. Across all epochs the ledger is 65 attempts, 55 valid completions, 422 calls, and a 9,240,999 token lower bound; the 13 usage-missing calls belong to older evidence and remain unknown, not backfilled.

### Behavior and transport attribution

`known-path-decisions-audit.json` supports the RulePlan finding. Repeat 8's plan reaches `position.itemIndex == items.Count` at the checkpoint after the two action-body steps, but the model explicitly returns `continuePlan`; the Runtime respects that request and consults again, and the model then returns NoAction. The additional consultation is properly counted. It is not evidence that the Runtime mistook plan exhaustion for task completion or skipped verification: verified entry/return evidence and the end-on-root obligation are still required before NoAction is accepted. Repeats 9 and 10 end in two consultations. Do not remove the slow repeat or retrofit the model's explicit continuation as an automatic Runtime shortcut.

Direct transport evidence remains appropriately qualified. The seven matched socket witnesses in `runtime-direct-proof.json` tie PID 85912 and DeepSeek port 443 to exact model-turn windows across the direct Step baseline; the artifact explicitly says this is not per-request packet capture. Each later trial separately passed the preflight listener PID and launch-environment hash checks, and all experiments match the frozen transport hash. The known Step/12 failed invocation still has no in-window socket witness, so its directness rests on the pinned service/environment and transport identity rather than a time-overlapping connection observation. This limitation does not indicate proxy mixing, but should remain visible; do not claim packet-level proof for every request.

### Final conclusion

The direct batch is internally consistent, usage-complete, tied to the registered Flash model and the direct service snapshot, and scoped to the known two-action path plus the tested two-candidate/four-action set. Three of four Plan groups pass; known RulePlan misses only the consultation ceiling. RulePlan/8's explicit empty-tail continuation explains the extra consultation while preserving correct Runtime completion and verification semantics. This does not establish an overall ADR-0053 performance PASS, full Settings traversal, a general speedup, statistical significance, or monetary savings. Do not add trials to chase PASS. Keep RUNTIME-PLAN-001 in VERIFY and retain all prior proxy, Pro, failed, and usage-incomplete evidence separately.
