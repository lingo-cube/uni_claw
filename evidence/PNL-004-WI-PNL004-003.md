## Result

Task Launch 现在有独立的 HTTP `POST /api/uniclaw-task/tasks/launch` 和 Panel `launch` 接缝。请求使用 S1 的 canonical 版本字段与对象化逻辑引用；Runtime 通过 `uniclawRuntime.createRun()` 产生 `runId`，随后建立 Task Instance、Product Session（若 Runtime 返回）、primary Host Session、逻辑 storage namespace 和分阶段 provenance。旧的 `POST .../instantiate` 保持原有行为。

## Boundary review

- `runId` 只接受 UniClaw Runtime 返回值，不能由 DSH session、目录名或 artifact 文件名推导。
- Launch 与五类只读 Query capability 分开；前端/Query 不直接读文件。
- `projectRef`、`testSetRef`、`taskRef` 在写入关系中保留逻辑 id；S2 manifest 的目录解析仍属于后续 Catalog Adapter，不把物理路径提升为公共契约。
- `sourceRevision`、metadata configured claim、launch stage 的 source/authority/availability/valueOrigin 通过边界校验并持久化。
