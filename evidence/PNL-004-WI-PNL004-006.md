# PNL-004 / WI-PNL004-006 — Launch contract and recovery remediation evidence

## Result

Launch stages now use the versioned `LaunchStageRecord` shape, including
`schemaVersion`, `contractVersion`, `stageId`, `recordedAt`, canonical
`availability`, and structured `diagnostic` data. The HTTP and Panel launch
responses expose a typed `TaskLaunchAck`; legacy instance string references are
kept only for compatibility. Test-set, task, project, version, and optional
`sourceRevision` references are resolved against the local manifest before the
Runtime is called. The local namespace is persisted as a logical
`LocalStorageNamespace` record. A partial retry reuses the original instance
and Runtime `runId`, then retries the missing Host binding. Runtime failures are
retained as pending/unknown and can proceed only through an explicit recovery
method; missing Product Session fails closed before Host creation.

## Boundary review

- Catalog resolution uses logical references and never returns the `testsets/` filesystem path.
- `runId` remains Runtime-owned; the retry path reuses it and does not call
  `createRun` again.
- `TaskLaunchAck.bindings` uses typed host and namespace references while the
  old instance projection remains compatible with existing DSH callers.
- The namespace adapter is still local repository storage; Host-owned catalog
  persistence and remote adapters remain outside this change.
- The production `uniclawRuntime` registration and the adapter from the logical
  launch request to `HostRunner.RunOnce` are not present in this repository;
  WI-PNL004-007 owns that next integration slice. Therefore this WorkItem is
  implementation-verified but remains pending for real end-to-end closure.
