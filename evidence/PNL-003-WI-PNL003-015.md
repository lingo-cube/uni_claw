# PNL-003 / WI-PNL003-015 — 真实 DSH Static Client 挂载缝审计

## 做了什么

审计真实 DSH static Client、Host RPC、Node Host wrapper 和通用 Workspace source 的调用链，判断是否可以直接进入 DSH 重启后的浏览器挂载验收。

## 原来的问题

Host wrapper 已能在 Node 侧装配 `panel → capabilities → Query Core → App → mount`，但现有 DSH `client.js` 是独立的 classic `window.__ModuleLoader__` React bundle，没有调用该 wrapper，也没有消费 `web/uniclaw-workspace` 的 Query Core/View Model/renderer。直接把 Node wrapper 塞进浏览器会引入 `createRequire` 和 Node 依赖；继续维护现有 client 则会形成第二套前端语义。

## 审计结论

判定：`UPSTREAM_DESIGN_CONFLICT`。

- DSH web plugin table 通过 `exports["./client"]` 加载 classic client；client 通过 `remote.$mount(contribution)` 注册并调用 `remote.uniclawTaskPanel.{workspace,session,artifact}`。
- `createDshWorkspaceHost` 是 Node-side assembly，当前没有 browser-compatible export，也未被 `client.js` 引用。
- shared Workspace 是 CommonJS；当前 package 没有浏览器构建/导出缝。
- 当前 client 的 strict codec helper 把 `parse` 放在 `create()` 返回值里；静态 Client 需要直接可验证的 `schema.parse`。

## 推荐下一步

增加显式 browser bridge/generated bundle：

1. 保持 `web/uniclaw-workspace/src/core`、features、ui、styles 为唯一 canonical source；必要时增加等价 browser export或生成式 bundle。
2. 将 `client.js` 收缩为 ModuleLoader 装载层、strict RPC descriptors 和 DSH slot 注册层。
3. bridge 只负责浏览器 mount 和事件转发；Host 继续负责 panel、ProductSession resolver、权限和 DSH session ref。
4. 用离线 bundle smoke、strict codec、Host mount、profile copy/restart 和浏览器主流程/失败路径证据闭合真实挂载。

## 结果

当前 Workspace 的 Node Host wrapper 和静态浏览器预览均已验证，但真实 DSH 重启后的共享前端挂载尚未完成；下一 WorkItem 必须先实现 browser bridge/generated bundle，不能把现有 DSH React UI 继续当作通用前端。
